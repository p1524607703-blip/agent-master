## 经验与判读要点
- **新增条数日间波动极大属正常**：9-01 仅 26 条、9-02 达 1663 条（差 64 倍）。原因是 Amazon 退货列表存在**录入延迟**——退款日的记录并非当天全部进入列表，往往次日才补齐。单次新增量小不代表漏抓，次日会自然补登。判读方法：看日报的 **Refund Date 分布**，若集中在最近 1-2 天即属健康；不必因条数暴涨怀疑脚本。
- **Authorization Date 跨度长（可达数周）不是 bug**：筛选器是 `REFUND_DATE_FILTER_GROUP`，授权早、退款晚是正常业务形态。切勿用 Authorization Date 判断增量边界。
- **游标命中页码是滞后指标（已作废，2026-09-04 起游标不再用于停止翻页）**：改版后游标仅作日志标记，`hitCursor=true` 仅表示"本次全扫途中重新见到了上次游标"，正常应为 true，不再表示提前停止。
- 写后必查三项：日报内部重复数（应为 0）、master 列数异常行（应为 0）、Refund Date 分布（应集中在近 1-2 天）。本次三项均通过（0 / 0 / 仅 08-31、09-01 两天）。
- master 现存 2 个历史遗留重复键（2 行冗余），非本次引入，暂不影响使用；如需清理可后续统一跑一次去重。

## 游标方案改版（2026-09-04 起生效）

- **改动**：`daily_pull.js` 由"命中游标即停"改为"全量翻页扫描 `LAST_7_DAYS` 整窗 + 按订单×ASIN 去重"，游标降级为纯日志标记。
- **动机**：FBA 退货列表按授权/订单时间排序，退款日刚进 7 天窗口但排序键更老的记录会排在游标**下方**被漏抓（见 9-04 首跑验证：旧模式会漏 ~75 条）。全窗扫描（筛选本就按退款日）闭合该缺口。
- **为何不加宽窗口**：紫鸟 UI 退款日筛选只有 6 个预设 radio（1/7/30/90/180/365 天），**无 9 天选项**（已查 `set_filter.js` 确认只能点 `LAST_7_DAYS`），故用 7 天整窗而非加宽到 8-9 天。
- **新判读要点**：
  - `stuck=true` 现表示"触达 UI ~1 万行硬上限"。9-04 跑满 10 页（1000/页）=10000 行后第 11 页重复即停——本店 7 天窗口≈10000 行，恰在阈值；**当日不代表丢数据**（已抓满整窗，143 条新全在窗内）。但高销量日窗口>10000 时，超出部分（最老退款日尾巴）会被截断→那些迟到补登可能漏抓，靠 `stuck` 告警 + SP-API 兜底。
  - `rowsCollected` 现=整窗行数（9-04 为 10000），非仅新增；`newRows` 才是真新增。
  - 运行变慢（139s vs 53s），因整窗重扫+去重；日级任务可接受。
- **残余风险与真·完整性方案**：UI 每窗口硬上限 ~1 万行，daily 与 weekly 深扫（30 天）均受此限，无法靠 UI 拿 >1 万行。要 100% 完整（尤其高销量日）须走 SP-API 官方 `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA` 报表（按日期区间拉取、无 UI 上限）——记忆中已记为全量历史正路。

## 紫鸟内 FBA 退货报告导出（CSRF 安全实测）

- **任务**：用 `ziniao-cli` 在紫鸟浏览器内只读导出 FBA 退货报告，避免亚马逊封控；验证一次 500 行可行性 + 实时更新应对。
- **CSRF 关键结论**：亚马逊 `/fba-return/refresh` 接口要求会话防伪令牌，**直接重放 fetch 会被拒**（返回壳页而非数据）。必须"借页面自身 CSRF"——在页内给分页下拉注入 `500` 项并 `dispatchEvent(change)`，让页面自己带令牌去拉数据，再读 DOM。
- **实测可行参数（店铺：川鹏2号 storeId 27661378824000）**：
  - 分页 `<select>` class = `a-native-dropdown a-declarative`，**默认每页 25 行**（不是 100）。
  - 注入 `option value=500` + 设值 + change → 页面渲染 500 行成功。
  - 翻页用文本为 `Next`（aria-label 为 null）的按钮 `click()`，正常推进到下一页不同数据。
  - 表格**无标准 `<thead>`**（表头在别处），`thead` 查询为空；数据行在 `tbody tr`，每行 **11 个 `td`**。
  - 11 列顺序：Marketplace / Order ID / [空白=商品图] / Product(名称+ASIN+SKU 合并一单元格) / Return Reason / Authorization Date / Refund Date / Unit Received Date / Disposition / Status / Action。
- **1000 行小批量测试结果**：2 页 × 500，全程串行、零并发、请求间隔 6–10s 随机抖动，总耗时 ~52s，**无报错、无封控提示**。合并 1002 → 去重 987（测试期间实时新增约 13 条导致跨页重叠，去重逻辑正确抵消"实时更新"问题）。
- **节流红线**：上次 Codex 被限流根因 = 4 并发 × 1000 行突发；本方案零并发 + 串行 + 冷却即可规避。
- **实时更新应对**：单次会话内页面不自动轮询（仅 notifications/tricorder 埋点）；跨时间才有新增 → 按日期窗口切分 + 末尾按整行去重即可。
- **脚本位置**（可复用）：`/tmp/fba_test/`：`inject.js`(注入500) / `extract.js`(读表) / `next.js`(翻页) / `run.js`(Node 编排) / `clean.js`(清洗CSV)。CLI 用全路径 `/opt/homebrew/bin/ziniao-cli`，`page exec` 走远程 ZClaw 通道（可靠），`page screenshot` 走本地 9481 Bridge（本环境间歇性故障，勿依赖）。

## 重要纠正：退货报告日期筛选只有预设，无自定义区间
- 之前建议"按任意日期窗口切片"是**未经验证的错误假设**，已更正。
- 实测：`REFUND_DATE_FILTER_GROUP` 是 radio 组，仅有 6 个预设值：LAST_DAY / LAST_7_DAYS / LAST_30_DAYS / LAST_90_DAYS / LAST_180_DAYS / LAST_YEAR。**页面无任何 `input[type=date]` / 日期选择器 / "date range / 自定义" 字样**。接口只吃这 6 个 preset，不接受任意 from/to 自定义区间。
- 推论：无法在 /fba-return 页面做自定义日期窗口切片。真正支持自定义区间的只有 SP-API 报表（方案一，用户暂不考虑）。
- 全量导出改用：串行翻页 + 6~10s 随机抖动 + 每 10~15 页插 30~90s 冷却 + 断点续跑(记录最后 Order ID) + 末尾整行去重 + 最新日单独补拉一次(抵消实时新增插入导致的跨页重叠/漏抓)。封控规避靠请求节奏，不靠日期。

## 排期时区修正（用户要求北京时间 09:00）
- **纠正上文第 48 行的说法**：`BYHOUR=9` 确实按本机时区解释，但本机是 `America/New_York`（EDT，UTC-4），本地 09:00 = **北京 21:00**，不是北京早上 9 点。用户实际要的是北京时间早上 09:00。
- **换算规则（rrule 按本机本地时间解释，需随夏令时切换）**：
  - 夏令时 EDT (UTC-4)：`BYHOUR=21` → 本地 21:00 = 北京次日 09:00 ✅ 当前生效
  - 冬令时 EST (UTC-5)：`BYHOUR=20` → 本地 20:00 = 北京次日 09:00
- 已把 `automation-1787733100468` 的 rrule 设为 `FREQ=DAILY;BYHOUR=21;BYMINUTE=0`，名称加后缀「（北京时间 09:00）」；验证 nextRunAt = 北京时间 2026-08-28 09:00 左右。

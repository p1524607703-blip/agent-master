- 现象：紫鸟浏览器（川鹏2号）打开 sellercentral.amazon.com 的 FBA 页失败（ERR_CONNECTION_RESET / 跳 `ziniao.block.*.com` 拦截页）。
- 根因定位：Surge 托管配置 `EdNovasCloud_surge (1).conf`（路径 `~/Library/Application Support/Surge/Profiles/`）的 [Rule] 第 107-111 行有 4 条 Amazon `DIRECT` 规则（用户为 Codex 导出 FBA Returns 加的直连）。紫鸟浏览器流量经 Surge 后被迫直连（本机 IP），而非走紫鸟店铺代理 IP，导致异常。

- 注意：该配置是 `#!MANAGED-CONFIG ... strict=true`，文件只读需 `chmod u+w` 才能改；12 小时托管同步可能覆盖，自定义区规则一般保留。若 Surge 开了增强/TUN 模式，`PROCESS-NAME` 规则可能不够，需把紫鸟加入 TUN 排除进程。
- 验证方法：改后用 `store open` 经 CLI 打开会被 `ziniao.block` 网关拦截（CLI 局限），真实验证须在紫鸟客户端手动重开店铺窗口看页面。若仍打不开，根因可能是川鹏2号代理 IP 被 Amazon 限流（需换紫鸟代理 IP），而非 Surge。

## 紫鸟 FBA 重测前端控制器（已建并验证）

- 位置：`/Users/panjinlong/Documents/agent-master/fba-controller/`（server.js 零依赖 Node + public/index.html + step-template.js）。监听 `127.0.0.1:8787`。功能：准备列表 / 完成列表 / 异常列表 / 开始 / 暂停 / 原因·包装下拉配置 / 实时日志。到"继续"前硬停、不提交；SKU 间 20-40s 抖动；网络错误等 60s 重试(最多3次)；暂停在每一步边界生效并回退当前 SKU 到队首。
- **两个关键集成坑（已修复，未来任何紫鸟自动化都会踩）**：
  1. **targetId 不能从 `store open` 拿**——它只返回 storeId/launchUrl/status(reused:true)，无 targetId。正确做法：`zclaw invoke visit_page --args '{"storeId":"27661378824000","url":"<FBA>"}'` → `data.data.targetId`（顺带导航并重置向导）。
  2. **`page exec` 返回被信封包裹**——结构 `{ok,data:{data:{result:"{...string...}",targetId,exceptionDetails}}}`。必须取 `data.data.result`（字符串）再 `JSON.parse`，不能解析顶层对象（顶层无 status 会误判失败）。脚本本身要 `return JSON.stringify(...)`（IIFE 内 return 合法；顶层 return 会 SyntaxError）。
- **重要运维教训**：`run_in_background` 启动的进程是 OS 级进程，聊天"暂停"只停 agent 循环、不停后台进程（之前 fba_batch.py 在暂停期间仍驱动浏览器即此因）。要让进程跨对话存活须用托管后台；普通 `node server.js &` 在 Bash 调用结束即被回收。停止用 `lsof -tiTCP:8787 | xargs kill` 或控制器的"暂停"。
- 启动：`/Users/panjinlong/.workbuddy/binaries/node/versions/22.22.2/bin/node server.js`（在 fba-controller 目录）。队列与状态持久化于 state.json。

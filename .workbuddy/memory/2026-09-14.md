## FBA 重测：审计重复提交 + 补齐「断电丢账」这个洞（v1.3.3）

### 用户问的两个问题，结论

1. **有没有重复提交？没有。** 审计证据：
   - submissions.csv 125 条 SUBMITTED，**同一 SKU 提交多次 = 0**
   - **101 个 case ID 全唯一**，无重复
   - state.done 91 条全唯一
   - 当前 pending ∩ 已提交 SKU = ∅
2. **关机有没有导致 CSV 漏收？这一轮没有，但机制上确实有这个洞。**
   - CSV 时间线只有两处断层（9/10 17:42 → 9/14 15:52 共 94h；9/14 16:32 → 9/15 08:50 共 16h），
     断层两侧都是「前一条 SUBMITTED → 下一条是新批次首条」，**没有悬空记录**
   - XH1 对账闭合：77 + 11 + 98 = 186 = 源表总数，无缺无重

### ⚠️ 挖出来的真洞：`inProgress` 不落盘

处理顺序是「先 `pending.shift()` 出队 → 再处理 → 成功后入 done」，
而 `saveState()` 只写 pending/done/failed/config/throttle，**inProgress 不写**，
`loadState()` 又强制 `state.inProgress = null`。

→ **处理中途断电/强杀/直接关机，这条在磁盘上彻底消失**（既不在 pending 也不在 done），
对账报「源表中从未进队列的 SKU」。若它其实已提交成功，下次按源表重新入队
（`/api/bulk` 只对 pending+done 去重）就会**再提交一次 = 真重复提交**。

**现场演示**：跑批途中导出对账表，就把正在跑的那条报成「从未进队列」并判不闭合（185≠186）。

修法（v1.3.3）：
- `saveState()` 增写 `inProgress` + `submitClicks`
- `loadState()` 残留恢复：残留 inProgress 且不在任何列表 → 计入 `failed`
  （原因「进程中断：…结果未知…」），**禁止自动重提**，出表落「异常明细」交人工核对
- 点「继续」**前**先写 `IN_FLIGHT` 审计行 + 立即 saveState，杀在点击后仍有痕迹
- `export_report.py` 认「在途」为第 4 个桶（已提交+异常+待处理+在途 == 源表总数）

已实测两个场景：残留能捞出 ✅ / 该 SKU 若已在 done 中则不重复计入 ✅

### 🔴 纪律（写给未来的自己）

**停机一律走 `POST /api/pause`，等日志出现「⏸」再关。**
直接关机 / `kill -9` 就是踩上面那个窗口。宁可多等 40 秒。

另：跑批途中做对账，在途那条会少 1 —— v1.3.3 起已能识别，不算异常。

### 补丁生效时机

server.js 的补丁**要重启服务才生效**。当前批次仍在用旧代码跑，
补丁从下次启动开始生效（未在跑批途中重启，避免打断正在进行的提交）。

| 条数 | 原因 | 处置 |
|---|---|---|
| 3 | 无可测量库存 | 真实业务失败，**救不了**，留 failed |
| 2 | `targetId` 解析失败（Bridge 瞬态） | **退回队列重试** |
| 1(+1) | 单 SKU 步数超限（网络卡导致空转烧步数） | **退回队列重试** |

—— 全部核对过 `submitClicks`，**都没点过「继续」= 未提交**，重试不会重复。

### 又抓到一个隐藏错误：探针 SKU 被记成"已提交"

早先那两条探针 `X004RULTQT` `X004RPUJAV`（解封关闭时跑的，停在"继续"前）
**被推进了 `done`**，出表时会虚增「已提交成功」2 条。同理捞出退回 pending。

⚠️ 教训：**探针法要慎用**——`STOP_BEFORE_CONTINUE` 分支会把 SKU 压进 `done`（`submitted:false`），
污染对账。要探针就别用正式 state，或探完立刻捞回。

### 处置动作（可复用清单）

1. `POST /api/pause` **先止血**（每条失败都消耗一个 SKU，要人工捞）
2. 确认 `status=paused` 且 `inProgress=None`，**再** kill node
3. 备份 `cp state.json state.before-rescue-<日期>.json`
4. 手工把可重试的从 `failed` → `pending`（`/api/remove` 只删 pending，**动不了 failed**）
5. 重启服务 → 解封 → 启动
6. **看门狗要重启**：它按**下标游标**跟踪新增失败，`failed` 变短后游标越界，
   新失败会被整段忽略（已修：游标越界时自动拉回）

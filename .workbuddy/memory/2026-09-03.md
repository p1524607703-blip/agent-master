## 广告报告下载 — 版本新鲜度坑（重要，已修 + 已入 skill）

- **背景**：上文 40-46 行记录的那批 5 份报告下载于美东 21:15-21:17（= 北京 09-04 09:15-09:17）。次日核对发现**其中 3 份是旧版**。
- **根因**：Amazon 每日订阅报告要到北京时间早上才跑完当天版本。3 份报告（广告活动 09:39 / 广告位 09:45 / 推广的商品 09:34）的「上次运行时间」**晚于**文件下载时间（09:15-09:17）→ 下载时新版还没生成，拿到的是 9/3 快照，**数据截止 09-02（T-2）**。
- **判读铁律**：30D 报告日期窗口末位应为 **T-1**；若是 **T-2** 就是旧版，必须重下。比看文件 mtime/大小可靠得多（旧版文件名、大小都"看起来正常"）。
- **时区陷阱**：后台显示 GMT+8，本地 mtime 是 America/New_York，夏令时差 12 小时；比对前必须换算到同一时区。
- **自洽验证**：搜索词(运行 09:11) 与 CPO(运行 08:39) 早于下载时间 → 数据到 09-03（T-1）；另 3 份晚于 → 到 09-02（T-2）。时间戳推断与日期窗口**完全吻合**，可互相印证。
- **脚本 bug 修复**：`download_ad_reports.js` 的 `run()` 原用 `[cli,...args].join(' ')` 拼串再交给 shell，而 `--script` 值是多行 JS（含大量空格）→ 会被 shell 拆碎参数。改用 `execFileSync(cliPath, args)` 传数组，修复后 3 份覆盖下载一次成功。
- **配置坑**：`loadConfig` 是 `Object.assign(base, JSON.parse(configFile))`，**config 文件的值会覆盖环境变量**，故 `AD_OVERWRITE=true` 在 config.json 里有 `"overwrite":false` 时**无效**。要覆盖下载必须改 config 文件或另建 config（本次新建 `config-chuanpeng-backfill.json`，overwrite:true，downloadTimeoutMs 420000）。
- **结果**：补下后 5 份窗口统一为 **2026-08-05 ~ 2026-09-03**（30 天），行数 16669/52355/606080/470194/115150。
- **已入 skill**：SKILL.md 新增「版本新鲜度核对（每次下载后必做）」章节，含判据、时区陷阱、实测案例、批量核对脚本、覆盖下载注意事项。

## 广告报告 — 新鲜度校验器 + 重试闭环（已落地实测）

- 新增 `verify_freshness.py`（skill 目录）：扫 CSV 数据日期列，**三重判据**交叉验证，解决"旧快照看起来正常"的漏判。
  - `LAG` 同批一致性：某报告日期 < 同账户其他报告众数 → 个别报告没跑完就被下载
  - `STUCK` 历史推进性：日期 ≤ 上次 state 记录 → 全部报告一起停滞（最强判据，补 LAG 盲区）
  - `OLD` 绝对底线：日期 < 美东今天 − 1 → 兜底
  - 退出码 0/1/2；`--remediate` 自动重下有问题的；`--json` 供定时任务解析；state 存 `.freshness_state.json`
- 新增 `pipeline.sh` 闭环：下载 → 校验 → 等待(WAIT_SEC，默认20分) 后重下(RETRY 轮，默认2)。定时时间没卡准报告生成时刻也能自愈。
- **踩坑1 — STUCK 同日误报**：初版判据是 `mx <= prev`，导致同一天重复校验时全部误报"未推进"，remediate 把 5 份报告无谓重下一遍。
  修复：加 `mx < today_iso`（数据已是美东当天则不算停滞）。回归验证：真实停滞场景仍 5/5 命中，同日重复 0 误报。
- **踩坑2 — 管道缓冲致日志错乱**：Python 在 `| tee` 下块缓冲、node 子进程不缓冲 → 下载日志跑到校验日志前面，
  一度误判成"步骤1没跳过已存在文件"。修复：pipeline 用 `python3 -u`。**自己拼管道务必保留 `-u`**。
- **反向测试很重要**：只验证"全通过"的校验器没有意义。构造 A(参差落后→LAG+OLD)、B(整体停滞→STUCK)、C(同日对照→不误报) 三场景全部实测通过。
- **报告生成时刻（川鹏）**：订阅报告在北京 08:21–09:47 陆续跑完 → 定时任务不能沿用现有北京 09:00，建议 **10:30 之后**触发。
- 幂等已验证：文件存在且 overwrite=false 时 5 份全部跳过，不重复下载。

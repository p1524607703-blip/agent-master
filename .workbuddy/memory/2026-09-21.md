## 踩坑
- **跨库不能 JOIN**：`app.*` 在 `amazon_ads`、`core.*` 在 `amazon_ads_v2`，覆盖计算必须搬到 Python。
- `psql -t -A` 回传字符串，`f"{n:>7,}"` 会 `ValueError: Cannot specify ',' with 's'` → 先 `int()`。
- 判「重复导入」不能用 `GROUP BY (日期,活动)` 数行数——一个活动一天本来就有 N 行（一行一商品）。要按**源文件 × (日期,活动) 逐组对账**，或看 `count(DISTINCT source_file_name)`。

- **psql 分隔符**：`-F '\t'` 遇到含制表符/换行的字段会 split 出异常长度 → 用 `-F '|~|'` 这种不会撞车的分隔符更稳。

**🔴 更深一层设计缺陷（记牢）**：surrogate 哈希输入 = `sha1(name | sku | parent_id)`，**依赖描述性字段**。某次导出缺 SKU 列、某次有 → 同一行两个哈希 → PK 随批次漂移 → upsert 永远合不上。根治方向：让 surrogate 只依赖稳定身份（如从 `campaign_id + ad_group_id` 派生），或入库前把"空值"统一归一成 NULL 再统一派生。

**防复发（比修数据更重要）**：同账户下同时存在 `empty_rows>0` 的文件与 `sur_rows>0` 的文件 → 立即告警。断言：任何 report_* 表内，同账户两类计数不得同时 >0。

### 二、六表有没有固定字段校验 —— 有，而且是六层

加载器 `import_account_30d_reports.py`：
1. **表头级**：required = `{广告主账户 ID, 日期, 广告产品, 广告活动编号}`；每类型另有 `Spec.fields` + `COMMON_ALIASES` 别名表；`unused_headers`（认不出的列）记 errors。
   🔴 **`errors` 非空 ⇒ 整文件拒收**（`import_one()` 首行 fail-fast，不是逐行跳过）→ **Amazon 一改表头，整个文件灌不进去**。这是最该防的运维风险。
2. **行级**：日期只认 `2026年9月21日`/ISO；整数列 `1.5` 直接抛错；`''`/`-`/`N/A`/`null` → None；缺 account_id/stat_date 计入 invalid_rows。
3. **PK 兜底**：空 PK 自动派生 surrogate（`__campaign__`/`__adgroup__`/`__target__`/`__advertised__`/`__purchased__` + sha1 前 20）。
4. **完整性**：逐账户要求 6 类各一份，账户数不限（旧版硬判 18 已废弃）。
5. **库身份断言**：`assert_database()` 校验 db+user，不符 `refusing write`。
6. **文件级幂等**：按 `file_hash` 查 import_batches，已成功 → `SKIP_HASH`。⚠️ 内容微变（一个字节）就重灌。

### 三、30D 导入是不是滚动覆盖 —— 是，upsert 天然滚动

`stage → COPY → ON CONFLICT (pk) DO UPDATE SET ... WHERE row_hash IS DISTINCT FROM excluded.row_hash`
- 同 PK 再现 → UPDATE；row_hash 一致 → 跳过（不计入 update）。
- **超 30 天老数据：不删、不截断**（全脚本无 TRUNCATE）→ 表下界 = 首次导入窗口起点，只会被更早导入推早。
- ⭐ **所以 `min(stat_date)` 是可用的残留探测器**：正常 30D 应为 T-29，看到 08-15 而窗口已是 08-22..09-20 → 有残留。
- 实测：六表批次数各 6 次，`report_start_date..end_date` = **08-22..09-20**；但 `min(stat_date)` 六表均 **08-15**（差值即残留）。
- ⚠️ **副作用**：`update_business` 只更新"本文件存在的列"（`col in active_fields`）→ 某次导出少一列，该列**保留历史值不覆盖**（防误清空设计），但会让你误以为"覆盖成功了"。

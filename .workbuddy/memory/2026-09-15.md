## 五层 data_level 的 NULL 成因 + 拆表建联方案（用户提问）

### 交付物
`amazon-ads-console/docs/五层分表设计与连接方案.md`（含实测矩阵、DDL、SQL 正反例）

### 结论一：NULL 有两个来源
1. **结构性 NULL（绝大多数）**：宽表把 5 个切面塞一张表，每层只填自己那列 → 填充率矩阵是**完美对角**。
   实测：campaign 层只填 campaign_name（ad_group_name 也全空）；placement 层填 placement；targeting 层填 target_id+target_match_type；advertised_product 层**只填名称**；purchased_product 层填 purchased_product_id。其余列 100% NULL。
2. **语义性 NULL（真问题）**：`advertised_product_id`(0/2457，上游就没这列)、`manager_account`(0/89801，加载器没映射)、`search_term_daily.ad_product`(0/102761，同上)、`purchased_product` LEFT JOIN 后 599 组合无转化。

### 结论二：五层的真实拓扑（实测数字）
- **投放侧四层共享同一底表粒度 = 2,457 个 (campaign_id, ad_group_id, stat_date) 组合**（campaign 层因 grain 是 campaign 故只 2,397）
- 平均每组合行数：advertised_product 1.00 / placement 2.78 / targeting 25.24 / purchased_product 8.66（唯一组合仅 1,858 → 599 个零转化）
- **下钻守恒铁证**：抽 3 个 campaign，campaign/placement/targeting/advertised_product 四层 sum(spend) 完全相等（15,389.72 / 10,042.74 / 9,665.61），第 3 个 advprod 差 3.30 系去重 192 行
- **`purchased_product` 无 spend/impressions/clicks（全 NULL）** → 属另一维度族，不能算 ACOS/CPC/CTR
- **可加性反证**：五层相加 spend = 510,987.06，真实值 127,762.80 → **4 倍膨胀**
- purchased_product 扇出分布：1 个 ad_group×date → 1~12 个 ASIN（1 个的只有 290 组合）→ 典型 N:N

### 结论三：拆表怎么建联
- **五张事实表之间不要建外键**（是切面不是层级实体；purchased 侧 N:N）。只在「事实表 → 维表」建 FK。
- 连接靠三件：① **退化维度键** `(account_id, ad_product, campaign_id, ad_group_id, stat_date)`；② `dim.*` 维表；③ `core.v_ad_*_daily` 视图
- campaign 层 `ad_group_id=''`，跨粒度对齐只用 (account_id, ad_product, campaign_id, stat_date)
- 正确写法：各层**先各自聚合再对齐**（同族用 FULL/JOIN 上去取一次总量；异族 LEFT JOIN + COALESCE 补 0）

### 🔴 验证时抓到两件事
1. **我第一版 CHECK 约束有 60 行违例**！`targeting` 层存在 60 行 `target_id`/`target_text`/`target_type`/`target_match_type` **全空**，`dimension_key` 退化成常量 `target:||`。
   源 CSV 对照：`川鹏_投放_30D_日期.csv` 62,021 行里**恰好 60 行「投放方案编号」与「投放方案」双空** → 是上游"无定向汇总行"，**不是脏数据**。
   → 教训：**CHECK 只能锁"排他"（不该填的必须空），不能锁"必填"**。修正版实测 0 违例。
2. **潜在静默丢数风险**：`target:||` 与 `advprod:` 都是**常量**，主键含 dimension_key → 同一 (campaign,ad_group,date) 出现 2 行以上退化键时会 `ON CONFLICT DO UPDATE` **静默覆盖**。当前冲突组合数 = **0**（安全），但 ad_daily 的 advertised_product 层 `advprod:` 恒为常量且恰好 1:1，是**运气不是设计**。
   → 修法：dimension_key fallback 加 `md5(row_content_hash)` 后缀，或导入前跑守卫 SQL。

### 其他实测
- 维表规模：dim.account 1 / dim.campaign 102 / dim.ad_group 106 / dim.target 3,267 / dim.product 3,695 / dim.placement 3
- 冗余量：`campaign_name` 存了 **89,801 遍**（实际仅 102 个 campaign）；`campaign_id=93118348042007`(XM2-KD7 头条目标值) 单条存了 **8,403 遍**
- **建议：现阶段不做物理拆表**（5 套分区维护成本 > 收益），优先「加 CHECK 约束 + 建 dim 维表 + 建视图」

## 追问：矩阵式宽表有什么用 / GPT 为什么这么设计 / 适不适合广告分析

### 实测：稀疏度与列覆盖（78 列 × 89,801 行）
- **整体稀疏 45.5%**（3,189,138 个空格子）；分层填充率：advertised_product 66.4% / placement 58.2% / targeting 58.3% / campaign 39.4% / purchased_product 38.5%

- **各层用列集合差异极大，没有任何两层相同**：campaign 32/78、purchased_product 30/78、placement 49/78、targeting 54/78、advertised_product 55/78
- **独占列**：campaign 独占 viewable_impressions / vctr_pct / long_term_sales / long_term_roas；targeting 独占 target_* 6 列；advertised_product 独占 7 列；placement 独占 placement；purchased_product 独占 3 列
- ⚠️ **订正**：全表死列是 **9 列**不是 7 —— 还要加 `source_file_name` / `source_file_hash`（lineage 列也全空 → **ad_daily 无行级文件血缘**，只能靠 batch_id）

### 结论（写进文档）
- 学名：**Generic Fact Table with Discriminator**（带判别列的同质事实表）。`dimension_key` 是其中唯一值得保留的聪明设计。
- **四个硬伤**：① 45.5% 空格 ② 列集是不规则子集不是矩阵 ③ `spend` 同列名不同口径（五层相加 = 4 倍膨胀）④ NULL 三义性（不适用/上游缺/真无转化）
- **GPT 为什么这么设计（5 条归因）**：① 从「导出文件」反推而非从「查询模式」反推（文档标题《基于实际导出数据》就是根因）② 误用"反规范化利于分析"（该建议只适用于列同质场景）③ **诊断错病根**：以为瓶颈是 JOIN，其实是口径混淆 ④ 追求覆盖性而非最小性 ⑤ 缺广告域成熟范式参照（Fivetran 分表 / dbt ad_reporting 统一粒度 / Google Ads Data Transfer 分表）
- **公平起见：它有一个真洞察** —— 广告花费在多视角下**可逆且守恒**（实测 campaign/placement/targeting 三层 sum(spend) 均 127,762.80），这在电商订单等普通业务数据里不存在。用 data_level 表达"同一事实的多视角切分"数学上贴切。⚠️ 但 `advertised_product` 层少 $64.14（去重 192 行）→ **守恒是近似的，必须记录偏差**。
- 问题不在洞察，在落地：**用「同一张表的多套行」表达多视角导致口径混淆；正确做法是「层级 grain + 独立表/物化视图」**。
- ✅ 适合：ODS 贴源层 / 单层查询 / 多视角对比 / 历史归档 ｜ ❌ 不适合：**自助 BI（拖 sum(spend) 错 4 倍且不报错，对 BI 工具"有毒"）** / 跨层下钻 / 口径治理 / NULL 语义 / 新人上手
- **演进路径**：阶段1 加 CHECK + 修死列映射 + 加表注释声明"ODS 层，业务走视图" + 建视图 → 阶段2 建 `mv_ad_*_daily` 物化视图（每张只带本层列）→ 阶段3 上 BI 时做真正星型
- ⚠️ 关键约束：**因为指标集不规则（viewable_impressions/long_term_sales 只在 campaign 层有），不能纯靠"最细粒度 rollup"生成上层，必须各自物化** —— 这才是"分表不可避免"的根本原因

### 05:00 EDT · 合规问询：QQ 邮箱收广告报告是否会触发店铺封控

用户问「用 QQ 邮箱收 Amazon 广告活动导出报告会不会触发封控」。**结论：本环节不会**。

**三条不封控的理由**
1. `ads-email-import/fetch_reports.py` 走的是 Amazon 自己签发的**预签名 S3 直链**（`X-Amz-Expires=172800`，48h）——URL 的定义就是「持有者免登录可下」。全程无登录、无 Cookie、无 Seller Central / Advertising Console 请求，S3 服务端无法回连到广告账户身份。
2. Amazon Ads 官方支持在「建报告 → delivery」直接指定收件人邮箱（官方文档原文：*you can designate a recipient of the report by entering an email address in the delivery section*）。
3. 广告报告是聚合数据（活动/投放/搜索词/推广商品），不含买家 PII，不碰 API 数据保护政策（DPP）。

**真正的风险在「投递路径」，不在邮箱品牌**
| 路径 | 判定 |
|---|---|
| Ads delivery 收件人直接填 QQ，Amazon 直投 | ✅ 推荐，邮件头干净 |
| Gmail 自动转发 → QQ（旧方案） | ⚠️ 划掉。邮件头留 `Received:` / `X-Forwarded-*` 转发链 |
| 多店铺报告邮件汇入同一 QQ | ⚠️ 弱关联线索，改子地址或一店一邮箱 |
| 该 QQ 承接登录验证码 / OTP | 🔴 红线。OTP 时序特征是关联判定硬指标 |

**已修订记忆**：`MEMORY.md` §6 原写「Gmail 无连接器 → 建议转发到 QQ」，**本日改为「直接在 Ads 报告 delivery 收件人填 QQ 邮箱，不走转发」**。

**信息污染提示**：中文 SEO 圈大量「QQ 邮箱必封号」文章是 Zoho / 企业邮箱软文（本次搜 5 篇，3 篇在卖邮箱），把「用 QQ 注册卖家账号」和「用 QQ 收报告邮件」混为一谈——前者有风险（域名历史包袱、撞库），后者基本无风险。

## 诊断：管理页「运营单双情况」运营人员/明细表都"不对"的根因

用户问「是不是因为没连数据库接口、没正式算 CPO」。**答：都不是**——接口真连（都查 RDS core.report_advertised_product_daily / report_business_parent_asin_period），列表的 CPO 也真算（花费÷业务报告订单），只是当天业务侧配不上 → 显示「—」。真因是下面 3 条。

### ① 运营人员不对 = **单账户口径**（主因）
- `/operator-cpo` 里 `_resolve(None, anchor)` 只解析出**一个账户**，再 `_operator_rows(aid, …)` 过滤 → 只出该账户的运营
- anchor 账户 = 洁博利 `7v98vtwh`（只有 AJ1/AJ2 活动）→ 列表只出「爱菊」
- 子娟(ZJ1)/雪敏(XM1,XM2)/雅婷(YT1)/丹丹(DD1)/雨珊(YS1) 的活动在**另两个账户**（欧德思 `ew58i919`、广告事实 `8j0l0xlz`）→ **列表里根本不出现**
- ⚠️ 三账户 max(stat_date) 全相同（09-14），`ORDER BY max(stat_date) DESC` **并列**→ anchor 账户实际不确定

### ② 多一行「未归属」$1,275.95 = 款号对不上主数据
- 广告表共 53 个父 ASIN，ASIN→组桥覆盖 52，**唯一未覆盖 = B0DTK7FK2M**
- 它的活动名 `AJ1-W2030 头条(W20W30)-0826(1)` → 解析款号 `W2030`，但主数据只有 `W20`（且归属 ZJ1）→ 匹配失败 → 未归属
- 活动名自带 `(W20W30)`，说明是**混装活动**，单款号模型承载不了

### ③ 明细表与列表对不上账 = **两套归属方法**
- 列表：按 **ASIN→运营组桥**（主数据款号推导）
- 明细 `operator_cpo_detail`：按 **`left(campaign_name,2) IN ('AJ')`** 前缀
- 实测 09-14 爱菊：明细合计 **$4,928.42** vs 列表行 **$3,649.44**，差 $1,278.98 = 未归属 1,275.95 + 脏行 3.03

### 明细表另外 4 个独立实现问题
1. **广告类型拆分写死造假**：`{"SB": 全花费, "SP":0,"SD":0,"STV":0}` → 明细页 SB 列永远吃掉全部花费（UI 确实渲染 DSP/SP/SB/SD/STV 列）
2. **全部订单/CPO/TACOS 硬编码 None** → 明细页永远没有 CPO（"没正式计算"只发生在明细，且是代码写死）
3. **用父 ASIN 当产品**（code=title=`B0…`），无款号、无商品标题
4. 未排除 `-1` 脏行（09-14 锚账户 7 行共 $3.03），列表排除了

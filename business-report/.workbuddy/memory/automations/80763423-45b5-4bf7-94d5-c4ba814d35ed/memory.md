## 经验
- **新失败模式「导航串页」**: `date not applied` + `pickers=[]` 时，先看汇总 JSON 里的 `state.url`。
  若 url 不是报告页（本次为 `sellercentral.amazon.com/fba-return`），说明页面导航跑偏，
  与「日期格式 M/D/Y vs Y/M/D」是两种不同根因，但**处理方式相同：直接重跑一次即可**。
- **transient vs 前置条件缺失的区分**: 紫鸟在跑 + 端口监听 + 登录态 OK 前提下的个别任务失败
  （download timeout / 串页导致的 date not applied）= transient，**应当自动重试一次**再上报；
  只有出现 `title=亚马逊 登录`、`TARGET_NOT_FOUND` 大面积爆发才是真前置条件缺失，才停止并人工介入。
- **别用裸 curl 探测 9480/9481 判断健康度**: 会返回 401/403（未带 API key），容易被误读成
  「API key 过期」而误报环境故障。真正的健康判据是脚本能否打开页面。
- **会话数偏低时的真伪判据（优先级高于单点基线）**: 看①是否多店同步连续多天下行 ②**行数是否仍在历史区间**
  ③后续日是否回升。三条全中即为真实业务波动。行数是最灵敏的错位探测器——日期抓错行数必先异常。
- 幂等生效：out/ 已有同名文件时自动跳过，重跑安全。
- 页面 usdCount 恒为 0 或波动（表格 UI 渲染不出），但 CSV 下载正常；就绪判定只看日期回读是否生效，别被 usd=0 误导。
- hint「可能尚未完全提供自 X 以后的数据」是常态提示，非错误，不必当警告上报。
- 本地 EDT 与北京时间跨日：本地周二晚 21:00 已是北京周三，周报触发条件会"看起来晚一天"，属预期，不是 bug。
- 脚本默认 backfill=3 天（`--backfill N` 可调，`--no-backfill` 关闭），中断几天后重跑会自动补齐。
- 偶发 `date not applied`：多为日期回读格式（M/D/Y vs Y/M/D）瞬时差异，直接重跑一次即可，不必改脚本。
- 验证数据真伪的手法：把可疑 CSV 移到 /tmp → 重跑（幂等会重新生成）→ 比对 md5/行数。一致即为真数据。
- 更轻量的真伪校验：周报会话合计 ÷7 与对应日均值对比，量级吻合即无需重抓。
- **校验 CSV 数字列必须用 Python csv（utf-8-sig）**，禁用 `awk -F','`：字段内含千分位逗号，awk 不解析引号，会把 "136,163" 切成两列导致合计腰斩并误报异常。

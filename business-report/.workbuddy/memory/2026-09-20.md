### Q2: 父子映射同步 148s 是否太久？→ 是的，根因已实测锁定（两个叠加原因）
- **元凶1（放大 148 倍）**: `sync_child_asin_mapping.py:141-224` 在事务内**逐行** `await app.execute()`。
  每次 execute = 一次跨公网 RDS 往返。实测 RDS 往返 29.3ms，逐行 UPDATE 27.8~46.1ms/条。
  4960 行 × 28ms ≈ 138s，与实测 148s 精确吻合；网络抖动时实测可达 228s。
- **元凶2（让更新量恒为全量）**: 第 187-191 行 `changed` 判定包含 `evidence` 全字段比较，
  而 evidence 里塞了 `scope_filter: account_scope` 和 `date_filter: stat_date`（第 121 行）。

## 映射同步性能优化已实施（用户批准「只做性能优化」）
- **方案抉择**: 采用 `executemany` 而**非** `unnest`。理由: executemany 用**逐字相同的 SQL 文本**，
  语义天然等价、风险为零；unnest 需重写 SQL 且收益不更优。
- **实测 unnest 高危**: 多数组长度不等时静默用 NULL 补齐（已验证 `unnest(['A','B','C'],['1','2'])`
  返回第 3 行 b=None），会造成数据错位且不报错 → 弃用。
- 改动文件: `amazon-ads-console/backend/scripts/sync_child_asin_mapping.py`
  - 新增三个模块级 SQL 常量（原文逐字搬运）
  - 把「事务内逐行 await execute」改为「先纯 Python 分桶 → 三类分别 executemany」
  - 分支判定（explicit 保留 / blocked_conflict 跳过 / identity 冲突阻断 / changed 才更新）完全不变
- **性能**: 单次 148s → **2.2s**；逐行 46.1ms/条 → executemany 270ms（**543×**）；
  每日 6 次同步（3店×2日）**约 15 分钟 → 12 秒**。
- **等价性验证（四项全过）**:

  3. 真实 6 次同步，各账户计数与改前一致（WHITIN 5050/5053... 等）

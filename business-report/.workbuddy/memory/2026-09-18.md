## 日期区间审计：toDate 是「双闭」而非脚本假设的「左闭右开」（重大结论）
- 用户怀疑 picker 显示 9/17~9/18 导致抓了两天。**实测推翻**：该文件是干净单日，但用户方向没错——配置本身确实错，只是错在别处。
- **根因**：Amazon 业务报告 URL 的 `toDate` **含当天（双闭）**，`br_pull.js` 的 `buildReportUrl()` 却按「右开」给它 +1。
- **为何日常没炸**：日任务 toDate = 太平洋当日 = 当天尚未出数 → 实际只拿到 1 天（侥幸正确）；周任务 toDate = 本周一 = 同理 → 7 天（侥幸正确）。
- **为何补洞炸了**：补洞的 D 与 D+1 **都是历史日、都已出数** → 真的抓了两天。
- 实测（欧德思美站，本次线上实拉，只读）：
  - 09-10单日 30,322 + 09-11单日 29,544 = **59,866** = 09-10~09-11 实测 59,866（精确相等）
  - 09-15单日 33,072 + 09-16单日 40,056 = **73,128** = 09-15~09-16 实测 73,128（行数 39 = 两日 ASIN 并集）
  - 09-17~09-17 = 32 行 / 36,571，与归档 09-17（URL 09-17~09-18）**完全一致** → 该文件干净
  - 09-07~09-13 = 217,681，与归档 weekly（URL 09-07~09-14）**完全一致** → 周报干净
- **污染清单**（`core.report_business_parent_asin_period`，共 **4 期间 / 538 行**，仅 09-10、09-11 ×2 店）：
  - WHITIN 09-10→09-11 311 行（batch 61）；WHITIN 09-11→09-12 136 行（batch 62）
  - BLOOMNEXT 09-10→09-11 55 行（batch 70）；BLOOMNEXT 09-11→09-12 36 行（batch 71）
  - 入库时间均为 2026-09-15 16:10:5x（一次性手工全量导入）；源文件为 09-13 21:31–21:44 补洞窗口产物。

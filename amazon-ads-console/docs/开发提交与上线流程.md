# CPO 开发、提交与上线流程

## 单向版本链路

本地开发 → 本地验收 → Git commit / push / tag → 准备候选版本 → 明确确认发布 → 服务器激活 → 健康检查。

- 本地项目：`agent-master/amazon-ads-console`；前端 5173，后端 8000。
- GitHub：`p1524607703-blip/agent-master`，当前为公开仓库。
- 开发分支：`cpo-develop`；候选版本使用 Git tag 固定 commit。
- `cpo-production` 在首次确认发布成功后建立/更新，不用尚未发布的候选版冒充生产版本。
- 提交保存版本，发布才切换线上。没有 push 后自动上线的任务。
- 服务器代码来自指定 Git commit，不接受工作目录文件复制；服务器只负责构建、运行与记录部署状态。

## 四个动作

### 1. 开发

在本地修改代码，使用独立的测试数据库做写入和数据测试。

当前本机旧 `.env` 及 15432 SSH 通道连接正式数据库，不能将其当成隔离测试环境。已增加 `CPO_ENV_FILE` 支持选择独立配置，开发配置模板为 `backend/.env.development.example`。复制为 `.env.development` 后填写独立本地测试实例的身份和配置，并初始化测试表结构/脱敏样本；模板本身不会创建数据库。

```bash
cd amazon-ads-console/backend
CPO_ENV_FILE="$PWD/.env.development" .venv/bin/python run_rds.py
```

另一个终端启动前端：

```bash
cd amazon-ads-console/frontend
npm run dev -- --host 127.0.0.1 --port 5173
```

不得在正式库做测试性导入、密码重置、映射变更。

### 2. 验收

执行构建，按本次需求确认界面、数据口径、权限和错误提示。用户要求测试时执行相应测试。对 CPO 映射和计算规则的变更，需要同时确认三项来源覆盖、未映射花费及是否满足最终 CPO 条件。

### 3. 提交

仅提交本次代码和文档。密钥、数据库连接配置、真实密码、报告、备份、上传文件和日志不进入 Git。

```bash
git add <本次文件>
git commit -m 'CPO: 描述本次改动'
git push origin cpo-develop
git tag <候选版本标签>
git push origin <候选版本标签>
```

提交完成后，可以继续开发其他版本；生产环境仍保持上一次明确发布的版本。

### 4. 准备与发布

本地先准备一个已提交、已存在于 GitHub 的版本：

```bash
python3 amazon-ads-console/scripts/release.py prepare <tag或commit>
```

此步骤会核对 GitHub commit/tree、同步 Git 对象、在服务器从该 commit 导出源码、按依赖锁定文件安装独立依赖、构建前端、校验每个源码文件，并只读检查两套数据库连接。**不切换线上，不重启现有服务。**

候选版验收完成，并明确确认“发布”后：

```bash
python3 amazon-ads-console/scripts/release.py deploy <同一个tag或commit>
```

发布先停旧服务并清 Redis 派生 snapshots（保留锁/会话），再将前后端切换到同一 Git 版本，重启、等待 startup warmup，预热最新 daily/monthly 并检查前端版本、后端鉴权响应及两库连接；失败时同样停候选、清快照、恢复旧代码/前端/unit、重启、预热并健康检查。部署记录区分成功回退和回退服务仍不健康的失败。

显式回滚使用 `python3 amazon-ads-console/scripts/release.py rollback <以前tag或commit>`。部署引擎固定当前工作树的已推送 HEAD（另经 GitHub/Git 校验），应用代码固定目标 tag/commit，避免老 tag 的旧部署脚本遗漏清缓存流程。日志、监控与主机配置见 [[CPO日志与发布运行手册]]。

GitHub 的 Git 协议当前连接不稳定，因此脚本使用经 GitHub API 核验的 Git commit/tree，并传输对应 Git 对象到服务器的部分 Git 镜像；不传未提交的本地源码。无论传输方式如何，源码均由服务器 `git archive <commit>` 导出，并逐文件校验 Git blob hash。

`deploy_frontend.sh` 现为兼容入口，也必须明确传入 `prepare|deploy` 与 tag/commit；不再以工作目录打包前端。

## 服务器目录与版本记录

```text
/opt/agent/cpo/
├── repository.git/          Git 对象镜像
├── releases/<commit>/      每版完整前后端源码、构建产物及独立依赖
├── current -> releases/... 当前正式版本（确认发布后建立）
├── tooling/                从 Git 提取的发布脚本
└── shared/                 私有配置、上传文件、部署记录
```

- systemd 配置来自该版本的 `deploy/cpo-console.service`。
- Nginx 保持服务静态页面和代理本机 8000；正式环境不运行 Vite 5173。
- 前端公开版本：`/version.json`，包含 commit、标签、构建/部署时间、健康状态。
- 服务器记录：`shared/current-release.json`、`shared/events.jsonl`，包含发布人、GitHub 仓库、版本和操作结果。
- 首次正式发布前，旧服务器仍属于历史复制部署：前端版本标识不能代表全部后端。不得将候选版本标为已上线。
- 代码回滚通过明确发布之前的 tag/commit 完成；数据库、业务映射和上传文件不随代码回滚。首次切换会先停止旧服务完成正在处理的请求，再同步原上传目录到共享目录，避免候选准备期间新增文件遗漏。
- 数据库结构变更另走 migration，业务映射数据另走审计记录。发布脚本不运行 seed、密码 reset、报告导入或数据库 migration。

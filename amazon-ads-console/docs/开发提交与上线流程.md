# CPO 开发、提交与上线流程

## 项目位置与环境

- 控制台项目：`agent-master/amazon-ads-console`，前端 `frontend`，后端 `backend`。
- 当前 GitHub 仓库：`p1524607703-blip/agent-master`；这是公开仓库。
- 前端开发端口：5173；服务器前端由 Nginx 提供，后端由 `cpo-console.service` 管理。
- 当前本地后端 `.env` 和日报导入项目配置连接腾讯云正式数据库。数据测试前必须改用独立测试实例/测试库、测试身份和独立配置，不能把当前本地通道当成隔离测试环境。
- 密钥、`.env`、真实账号密码、数据库备份、客户原始报告和日志不得提交到 GitHub。

## 运行链路与现状（2026-09-30）

1. 收到广告日报与业务日报。
2. 校验账户、日期、报告类型、字段和重复文件后，入库 `amazon_ads_v2.core.report_*`。
3. 根据应用库产品映射及运营归属规则匹配人员；未匹配/冲突记录留在质量审计中。
4. CPO 服务在查询时汇总花费及业务订单，计算 CPO；不是每日定时生成一份已结算结果。
5. 报告缺失、映射冲突、未归属花费会限制最终 CPO。三项来源完整并不等于费用结算已通过。

已存在正确事实表导入脚本：仓库外 `amazon-ads-data/scripts/import_account_30d_reports.py`，导入六类账户级广告报告，支持预解析 `--dry-run`、文件哈希跳过与更新导入。业务日报仍需要对应的独立导入路径。

旧本机 `com.panjinlong.amazon-ads-scan` 处于暂停状态，写入目标与当前事实表结构不一致；服务器未安装日报自动入库任务。用户已决定将每日报告自动入库交给后续自动化插件，本次不恢复旧任务。插件需对接当前事实表，并涵盖广告及业务两路导入、失败处理和成功记录。

## 本次页面修复

- 取消概览及店铺筛选器内写死的历史日期。
- 默认查看所选店铺最新入库数据，日期框显示实际返回日期。
- 切换店铺、点击“最新数据”、每分钟可见页面刷新和重新切回页面时跟进最新日期。
- 手动选择历史日期后保留该日期，避免自动刷新改变历史查询。
- 概览接口失败时显示错误，不以演示数据替代真实数据。
- 管理层、超级管理员默认进入 CPO，运营人员保持进入自己的 CPO 页面；侧边栏 CPO 置顶。

## 后续开发与上线

3. 按需求执行构建；用户要求测试时再执行对应测试。
4. 只提交本次有关的代码、文档，推送 GitHub 后按提交/PR 跟踪进度。

```bash

```

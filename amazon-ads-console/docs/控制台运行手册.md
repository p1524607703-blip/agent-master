## 一、当前架构：双库 + 双 DSN

```
┌─ 应用库 amazon_ads ────────────┐   ┌─ 数据仓库 amazon_ads_v2 ───────────────────┐
│ iam.roles / iam.users          │   │ core.report_campaign_daily          2,397 │
│ iam.user_sessions              │   │ core.report_placement_daily         6,829 │
│                                │   │ core.report_targeting_daily        62,021 │
│ ← auth（asyncpg 直连）          │   │ core.report_advertised_product_daily 2,457 │
└────────────────────────────────┘   │ core.report_purchased_product_daily 16,097 │
                                     │ core.report_search_term_daily      102,761 │
                                     │ core.ad_daily（ODS 宽表，保留不动）        │
                                     │ ← 业务读（psql 子进程）                     │
                                     └───────────────────────────────────────────┘
        PostgreSQL 不支持跨库 JOIN → 应用层双 DSN，JOIN 在 Python 里做
```

环境变量（`backend/.env`）：

| 变量 | 指向 | 用途 |
|---|---|---|
| `DATABASE_URL` | `…/amazon_ads` | 身份与角色、会话 |
| `RDS_DATABASE_URL` | `…/amazon_ads_v2` | 广告活动事实表 |

`run_rds.py` 导出两组 PG 环境变量：`PG*`（应用库）、`RDS_PG*`（数据仓库）；
`app/services/rds_query.py` 只读 `RDS_PG*`。

## 二、启动

两个进程，都要用**工具后台模式**跑，不能用 `nohup &`（会被回收）。

```bash
# ① 后端：8000
cd amazon-ads-console/backend
.venv/bin/python run_rds.py
# 启动时会打印两行，确认两个库都对：
#   [auth] app  db = amazon_ads_admin@…:5432/amazon_ads
#   [data] data db = amazon_ads_admin@…:5432/amazon_ads_v2

# ② 前端：5173
cd amazon-ads-console/frontend
npx vite --port 5173 --host 127.0.0.1
```

访问 `http://127.0.0.1:5173`，用下面任一账号登录（`seed_rds_iam.py` 种入）：

| 账号 | 角色 | operator_code |
|---|---|---|
| `admin` | super_admin 超级管理员 | — |
| `boss` | management 管理层 | — |
| `op_zj1` / `op_aj1` / `op_yt1` / `op_xm1` / `op_xm2` / `op_dd1` / `op_aj2` / `op_ys1` | operator 运营 | 对应运营组 |

密码由 `backend/scripts/seed_rds_iam.py` 生成并**只打印一次**，未落库明文。
忘记密码就重跑（已存在的账号会跳过，不会覆盖），或直接改哈希。

```bash
cd amazon-ads-console/backend
python3 scripts/seed_rds_iam.py                        # 随机密码
ADSIGHT_SEED_PASSWORD='你的固定密码（≥12位）' python3 scripts/seed_rds_iam.py
```

> ⚠️ 该脚本有**只允许 RDS 主机**的硬护栏（与 `seed_local_iam.py` 的 localhost 护栏方向相反），不会误写本地库。

| 接口 | 状态 | 数据来源 |
|---|---|---|
| `GET /api/health` | ✅ | `SELECT 1` |
| `GET /api/reports` | ✅ 真实 | 6 张 report 表的覆盖与血缘完整性 |
| `GET /api/dashboard/overview` | ✅ 真实（广告侧） | `report_campaign_daily` |
| `GET /api/dashboard/trend` | ✅ 真实（广告侧） | `report_campaign_daily` |
| `GET /api/operator-periods` | ✅ 真实 | `report_campaign_daily` 的实际入库日期 |
| `GET /api/operator-cpo` | ✅ 真实（广告侧） | 按 `campaign_name` 首段聚合运营组 |
| `GET /api/operators/{name}` | ✅ 真实（广告侧） | 按父 ASIN 下钻 |
| `GET /api/products` | ✅ 真实（广告侧） | `report_advertised_product_daily` 父 ASIN |
| `GET /api/auth/*` | ✅ | `iam.users` / `iam.user_sessions` |

### 业务侧为什么是「—」

`全部订单 / 综合 CPO / TACOS` 的分母来自 **Seller Central 业务报告**（按父商品），该报告**尚未入库**。
没有分母，CPO 算不出来，因此这三个字段一律返回 `null`，前端渲染成「—」，
并在 `quality_flags` 里带 `business_report_not_loaded`——**绝不用 0 或估算值填充**。

补上业务报告后（管线见 `br_to_rds.py`），只需在 `report_data.py` 里给这三处接上分母。

## 四、运营组口径

运营维度取自 `campaign_name` 的首段（如 `ZJ1-W30 头条 低价` → `ZJ1`），按 2 字符前缀归并到人名：

| 前缀 | 人名 | 前缀 | 人名 |
|---|---|---|---|
| ZJ | 子娟 | DD | 丹丹 |
| AJ | 爱菊（AJ1+AJ2 合并） | YS | 雨珊 |
| YT | 雅婷 | LB | 丽斌 |
| XM | 雪敏（XM1+XM2 合并） | XH | 鑫华 |

实测当前数据覆盖 8 个组：ZJ1 / AJ1 / AJ2 / YT1 / XM1 / XM2 / DD1 / YS1。

## 五、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面全空、无报错 | `frontend/src/api/client.ts` 所有请求 `catch → fallback`，会**静默吞错** | 看后端日志，别信 UI |
| 看板账户选「川鹏」却有数据 | 后端做了自适应回退：请求的账户/日期无数据时用最新的，并标 `fallback` 质量标记 | 正常行为，审计栏会显示实际用的账户 |
| `RDS_PG* is not configured` | 用 `uvicorn app.main:app` 直接起，没走 `run_rds.py` | 用 `run_rds.py` 启动 |
| `unsupported operand type(s) for \|` | `backend/.venv` 是 Python 3.9，不支持 `str \| None`（PEP 604） | 注解用 `Optional[str]` |
| 后端进程起来又消失 | `nohup &` 在本机被回收 | 用工具后台模式 + `tee` 日志 |

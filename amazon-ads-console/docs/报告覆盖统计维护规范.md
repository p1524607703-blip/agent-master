# 报告覆盖统计维护规范

`GET /api/reports` 仍仅允许管理层和超级管理员访问。接口只读取仓库中的 `core.report_coverage_snapshots` 小表，以及 `core.import_batches` 的成功批次修订号，不再扫描六张事实表。接口沿用卡片数组结构，增加成功统计时间、快照修订、当前源修订和刷新状态。

行数、日期范围、来源完整性来自当前事实表的精确聚合。导入批次的 `valid_row_count`、`inserted_row_count`、`updated_row_count` 等累计数不能作为事实行数。维护扫描确认 `source_file_name NOT NULL` 后才使用 `count(*)` 计算来源行数；允许空值的旧表仍精确统计 `count(source_file_name)`。

## 状态约定

| 状态 | 含义 |
| --- | --- |
| READY | 当前成功批次修订与成功统计修订一致，且维护任务成功 |
| STALE | 有旧的成功快照，但源修订变化、正在刷新或最近刷新失败；保留旧值并标明旧快照时间 |
| PENDING | 首次统计尚未完成、迁移未应用或快照版本尚未支持；行数是 `null`，不能显示为零 |
| FAILED | 尚无成功快照且维护失败；行数仍为 `null` |

空事实表成功统计后可以显示零行。数据库不可用时接口报错，前端显示读取失败；不以空数组或缓存中的旧 READY 代替错误。刷新超过 15 分钟仍未完成的标记按中断失败显示。

## 安装与执行

迁移文件 `backend/migrations/20261022_report_coverage_snapshots.sql` 仅应用到数据仓库 `amazon_ads_v2`。HTTP 查询角色只授予新表 `SELECT`；独立维护角色拥有该小表的读写权限和源事实表的只读权限。生产定时服务使用本机 `postgres` 用户和 Unix socket，不加载 HTTP 只读账号或提升其权限。

首次初始化或人工核验：

```sh
sudo -u postgres /usr/bin/python3 /opt/agent/cpo/current/amazon-ads-console/backend/scripts/refresh_report_coverage.py --dsn postgresql:///amazon_ads_v2 --force
```

只重试一张表（可以重复 `--table`）：

```sh
sudo -u postgres /usr/bin/python3 /opt/agent/cpo/current/amazon-ads-console/backend/scripts/refresh_report_coverage.py --dsn postgresql:///amazon_ads_v2 --table core.report_targeting_daily --force
```

脚本只依赖 Python 标准库与 `psql`。输出标准 JSON，包括状态、刷新/跳过/失败表名、快照数量及各表快照修订、成功时间、账户数量、事实行数；不输出源数据值或原始 SQL 错误。失败返回非零退出码。首次无摘要会自动初始化；平时默认只刷新修订变化或待恢复的表。`--force` 仅人工初始化/核验时使用。

安装 `deploy/infra/cpo-report-coverage.service` 与 `.timer` 到 systemd 后启动 timer。每五分钟检查一次，未变化只读小表。每次至多一个维护实例持有 PostgreSQL session advisory lock，跨进程和跨机器互斥；单次只扫描一张表，并关闭查询并行。单表语句默认 300 秒，全任务上限 1200 秒，服务预留 10 秒退出时间；使用低进程和 IO 优先级。失败后 15 分钟内跳过重扫，防止频繁失败加重数据库负载。

每张表在独立 REPEATABLE READ 事务中一起读取事实与源修订，成功后原子替换摘要。刷新开始与失败标记分开提交，因此失败不覆盖上次成功 payload。进程被杀导致的刷新中标记在 15 分钟后显示中断，并允许下次维护恢复。

## 数据发布衔接与限制

报表发布成功后可主动运行同一独立脚本；timer 作为兜底。当前发布器按账户和实际日期区间替换，保留区间外历史，因此不能只用新文件行数覆盖全历史摘要。本轮不修改外部发布器。

新成功批次的 `max(batch_id)` 是失效标记，并非事实计数。若修复历史数据时不新增成功批次，必须在同一运维流程中显式执行 `--force`，不能期待相同修订自动识别任意手工 SQL。后续如需更低维护 IO，可在统一入库事务内维护精确每日摘要，且必须先验证区间外历史守恒。

## 验证与回滚

`backend/tests/test_report_coverage_pg.py` 使用隔离临时 PostgreSQL 和合成数据，运行与生产一致的标准库/psql CLI，验证精确计数、允许空值的来源统计、修订变化、未变化跳过、单表超时保留旧值、失败退避、人工恢复与并发锁。

发布验收检查管理接口首访/重复读取延时、各账户六类报表卡片与精确摘要一致、快照修订与当前成功批次一致，以及运营角色仍为 403。回滚时停止 timer 并回滚应用版本；新增摘要表可以保留，旧版不会读取它，不影响源事实和财务算法。

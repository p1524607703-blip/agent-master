# 架构评审：矩阵式宽表到底适不适合广告活动分析

> 2026-09-15 · 所有数字来自 `amazon_ads_v2` 实测（78 列 × 89,801 行的逐列填充率统计）
> 前置文档：`数据架构与ER图.md`、`五层分表设计与连接方案.md`

---

## 一、先给它一个准确的学名

这不是"矩阵表"，标准叫法是 **Generic Fact Table with Discriminator**（带判别列的同质事实表），业界也有叫 **wide table / OBT (one big table)** 的。

结构特征：

| 手段 | 作用 |
|---|---|
| `data_level` 列 | 判别器（discriminator），标记这一行属于哪套粒度 |
| `grain_level` 列 | 粒度说明（campaign / ad_group） |
| `dimension_key` 列 | 字符串维度键，让**一套复合主键**能覆盖 5 种不同粒度的唯一性 |
| 78 列超集 | 5 份报告字段的并集 |

最有价值的设计其实是第 3 条 —— **`dimension_key` 是个真聪明的妥协**：它让"一张表去重"这件事在数学上成立，不用 5 套主键。这个设计**值得保留**。

## 二、实测出来的四个硬伤

### 硬伤 1：45.5% 是空格子

| data_level | 行数 | 有值格子 | 填充率 | 用到列数 |
|---|---:|---:|---:|---:|
| advertised_product | 2,457 | 127,286 | 66.4% | 55 |
| campaign | 2,397 | 73,640 | **39.4%** | 32 |
| placement | 6,829 | 310,008 | 58.2% | 49 |
| purchased_product | 16,097 | 482,910 | **38.5%** | 30 |
| targeting | 62,021 | 2,821,496 | 58.3% | 54 |
| **合计** | **89,801** | **3,815,340** | **54.5%** | — |

**3,189,138 个格子是空的。** 其中 `campaign` 层和 `purchased_product` 层填充率不到 40%——三层里有两层在"半张空表"上跑。

### 硬伤 2：这根本不是"矩阵"，是 5 个**不规则子集**的并集

63 个**业务列**（78 总列 − 15 元数据列）按被几层使用来分组（实测）：

| 被几层使用 | 列数 | 占比 |
|---|---:|---:|
| 5 层共用 | **5** | 8% |
| 4 层 | 19 | 30% |
| 3 层 | 11 | 17% |
| **1 层独占** | **21** | **33%** |
| **0 层（死列）** | **7** | **11%** |

- **真正的"公共矩阵"只有 5 列**：`campaign_name`、`budget_currency`、`purchases`、`sales`、`new_to_brand_purchases`
- **21 列（1/3）只为某一层服务**，其中 `advertised_product` 独占 7 列、`targeting` 独占 6 列、`campaign` 独占 4 列（`viewable_impressions` / `vctr_pct` / `long_term_sales` / `long_term_roas`）
- **7 个业务列从来没有过值**：`manager_account`、`campaign_state`、`global_campaign_id`、`advertised_product_id`、`advertised_product_marketplace`、`promoted_acos_pct`、`new_to_brand_acos_pct`

> ⚠️ **若按全部 78 列统计，死列是 9 个** —— 还要加上 `source_file_hash` 和 `source_file_name`。
> 这两列是**血缘列**，它们的空值意味着 **`ad_daily` 没有行级文件血缘**，只能靠 `batch_id` 回溯到批次，追不到"这一行来自哪个文件"。这是一个独立的数据治理缺口。

各层实际用到的列集合大小差异极大，**没有任何两层用同一套列**：

| data_level | 含元数据列 | 仅业务列 |
|---|---:|---:|
| campaign | 32 / 78（41%） | 19 / 63（30%） |
| purchased_product | 30 / 78（38%） | 17 / 63（27%） |
| placement | 49 / 78（63%） | 36 / 63（57%） |
| targeting | 54 / 78（69%） | 41 / 63（65%） |
| advertised_product | 55 / 78（71%） | 42 / 63（67%） |

→ 结论：**宽表的"一套列"假设根本不成立**。5 份报告的字段集天然不同（Amazon 广告活动报告没有"匹配类型"，投放报告没有"广告位"）。

### 硬伤 3：`spend` 这一列，在 5 层里是 5 个不同的度量

这是最危险的一条。**列名相同，口径不同**：

| 查询 | 结果 |
|---|---:|
| `WHERE data_level='campaign'` 的 `sum(spend)` | 127,762.80 |
| `WHERE data_level='placement'` 的 `sum(spend)` | 127,762.80（相等，是同一个总量的拆分） |
| `WHERE data_level='targeting'` 的 `sum(spend)` | 127,762.80（相等） |
| **不加 WHERE，`sum(spend)`** | **510,987.06（错 4 倍）** |

任何不懂规则的人在 Metabase / Tableau / Excel 里拖一下 `sum(spend)`，直接得到一个错 4 倍的数字。**这张表对自助 BI 工具是有毒的**——它不会报错，它会给你一个看起来很合理的错误答案。

### 硬伤 4：同一个 NULL，三种完全不同的含义

| NULL 出现在 | 真实含义 | 占比 |
|---|---|---:|
| `campaign` 行的 `target_id` | **该层不适用**（结构性） | 绝大多数 |
| `advertised_product_id` | **上游就没给**（缺列） | 全部 |
| LEFT JOIN 后 `purchased_product` 为 NULL | **真的没有转化** | 599 个组合 |

BI 工具和下游用户**无法区分这三者**。数据治理上这是大忌：缺失语义必须可表达（要么用 `NOT NULL DEFAULT ''` + 哨兵值，要么用单独的表）。

## 三、工业界标准做法是什么

| 方案 | 代表 | 做法 |
|---|---|---|
| **按报告分表** | Fivetran / Stitch（Google Ads、Facebook Ads connector） | `campaign_report` / `ad_group_report` / `keyword_report` 各一张 |
| **统一粒度 + rollup** | dbt `ad_reporting` 包 | 事实表固定在最细粒度（`ad_report`），上层用 rollup 模型聚合 |
| **按报告分表** | Google Ads → BigQuery Data Transfer | `ads_Campaign_*` / `ads_AdGroup_*` 分表 + 视图合并 |
| **本方案** | 本项目 | 5 层混装一张 78 列宽表 + `data_level` 判别 |

共同点：**不用"同一张表的多套行"来表达"多视角"，而用「分表」或「维度」表达。**

---

## 四、GPT 为什么会这么设计（诚实归因）

排掉"它笨"这种没信息量的解释，真正的原因有五条：

### 1. 它是从「导出文件」反推 schema，不是从「分析问题」反推

架构文档的标题就是《**基于实际导出数据**》。这是根因。
GPT 拿到 6 份 CSV，看到字段有交集 → 求并集做成宽表。这是**归纳式设计**（从数据形状倒推结构）。

而 schema 设计应该是**演绎式**的（从查询模式倒推结构）。正确的起点问题是：
> "分析师会怎么问问题？" → 从活动下钻到广告组 → 每一跳都是跨 grain → 所以**每个 grain 应该是一张独立的表/视图**。

### 2. 训练语料里的 "wide table / denormalize for analytics" 偏好被误用了

"反规范化利于分析"这条建议在**列同质**的场景（事件流、日志、指标快照）是对的。
在**列异质**的场景（不同报告的不同字段集）就错了——因为"反规范化"的前提是"这些列属于同一实体"。

GPT 没区分这两种情况。

### 3. 诊断错了病根：以为瓶颈是 JOIN，其实是口径混淆

LLM 有个朴素直觉："拆表要 JOIN，JOIN 麻烦，所以一张表全装"。
但广告分析的真实瓶颈**从来不是 JOIN 性能**（5 张几万行的表 JOIN 毫无压力），而是：

- 口径混淆（`spend` 在 5 层里定义不同）
- 重复计数（JOIN 后 SUM 直接 4 倍膨胀）
- NULL 语义丢失

**把复杂度从"JOIN 写法"挪到了"口径正确性"，还挪到了没人会读的地方。**

### 4. 追求覆盖性而非最小性（宁多勿缺）

LLM 设计的典型倾向：怕漏字段，于是设计超集。
代价就是实测出来的 **7 个死列 + 21 个独占列**。
宽表还有一个副作用：**多加一列不会报错**，所以没人会去验证"这列到底有没有用"。

### 5. 缺少广告域成熟范式的参照

Fivetran / dbt `ad_reporting` / Google Ads Data Transfer 都有现成的分表或统一粒度范式。这套设计明显没有参照它们。

## 五、那它真的一无是处吗？——不，有一个洞察是对的

**公平起见，必须指出这个设计里有一个真正正确的洞察：**

> **广告数据的花费，在多个视角下是「可逆且守恒」的。**
>
> 实测：同一个 campaign，`sum(spend)` 在 campaign / placement / targeting / advertised_product 四层分别是
> `15,389.72` / `15,389.72` / `15,389.72` / `15,389.72` —— **四层完全一致**。
> 三层汇总口径相等：127,762.80 = 127,762.80 = 127,762.80。

**这在普通业务数据里几乎不存在。** 电商订单按商品拆分后总额不会还相等，用户按渠道拆分后 DAU 也不会相等。但广告花费可以——因为它是**同一批曝光/点击在不同维度上的重新切分**。

所以"用 `data_level` 表达同一事实的多视角切分"，**在数学上是贴切的**。这个洞察，传统星型模型反而不容易表达（星型要建 5 张事实表，还得自己保证它们的总额相等）。

> ⚠️ 唯一的不完美：`advertised_product` 层实测少了 $64.14（因为去重 192 行），所以"守恒"是**近似**的，不是精确的。这个偏差必须被记录，否则对账时会翻车。

**问题不在洞察，在落地方式**：用「同一张表的多套行」表达多视角 → 口径混淆；
正确做法是**用「层级 grain + 独立表/物化视图」表达多视角** → 口径隔离但守恒关系仍可校验。

## 六、结论：适合什么，不适合什么

### ✅ 适合（约占 30%）

1. **作为 ODS / 贴源层**（同时满足"不丢字段"和"一次 COPY 入库"）
2. **单层查询**：`WHERE data_level='campaign'` 配视图，等价于一张干净的表
3. **多视角对比 / 归因回溯**：同一花费按广告位看 vs 按定向看，宽表切起来方便
4. **历史归档**：`search_term_target_period` 那种月期间冷数据，混装不影响
5. **表达"可逆守恒"这一广告数据特性**（这是它唯一的原创价值）

### ❌ 不适合（约占 70%，且恰恰是最重要的场景）

1. **面向业务的自助 BI** —— 拖 `sum(spend)` 就错 4 倍，且**不报错**。致命
2. **跨层下钻**（广告分析最高频的动作）—— 每跳都要重写 WHERE 且必须防重复计数
3. **口径治理** —— 列名相同定义不同，元数据层无法表达"该指标适用哪一层"
4. **NULL 语义表达** —— 三种含义共用同一符号
5. **新人上手** —— 78 列 + 21 个独占列 + 7 个死列，看十分钟也判断不出该用哪列

**一句话结论：**

> 作为**数据接入层（ODS）**它是合格的，甚至那个"可逆守恒"的洞察是加分的；
> 作为**分析服务层（ADS）**它不合格 —— 因为它把"用哪个口径"这件最重要的事，交给了使用者的自觉。

## 七、正确的演进路径

### 阶段 1 · 止血（保留宽表，不动结构）

1. 加 `ad_daily_level_cols_check`（见 `五层分表设计与连接方案.md` §3.6），把结构性约定变成数据库强制
2. **修死列的映射**（7 个业务死列里，6 个是加载器漏映射：`manager_account` / `campaign_state` / `global_campaign_id` / `advertised_product_marketplace` / `promoted_acos_pct` / `new_to_brand_acos_pct`；`advertised_product_id` 是上游没有，修不了）
   **另外补 `source_file_name` / `source_file_hash` 的写入** —— 目前全空，等于没有行级血缘
3. **给宽表加角色定位**：在表注释里写明「**本表是 ODS 层，业务查询请走 `core.v_ad_*_daily` 视图**」
   ```sql
   COMMENT ON TABLE core.ad_daily IS
   'ODS 贴源层：5 类 data_level 混装。禁止直接聚合，业务查询请用 core.v_ad_*_daily 视图。'
   ```
4. 建 `core.v_ad_*_daily` 五个视图（业务唯一入口）

### 阶段 2 · 口径隔离（逻辑分表 → 物化视图）

为每个 grain 建**物化视图**，从宽表物化出来：

```sql
CREATE MATERIALIZED VIEW core.mv_ad_campaign_daily AS
SELECT account_id, ad_product, campaign_id, stat_date,
       campaign_name, campaign_state,
       impressions, viewable_impressions, clicks, spend, purchases, sales,
       new_to_brand_purchases, long_term_sales,
       ctr_pct, vctr_pct, cpc, cvr_pct, cpa, acos_pct, roas,
       new_to_brand_cpa, long_term_roas            -- ← 只带本层真正有的列
FROM   core.ad_daily
WHERE  data_level = 'campaign';
```

好处：
- 每张物化视图的列集**正好等于该层用到的列**（19~42 列，不再是 78 列）
- 业务侧拖 `sum(spend)` **不可能错**，因为每张表只有一个口径
- 可建索引、可单独授权、可加注释

⚠️ **注意**：因为**指标集不规则**（`viewable_impressions` / `long_term_sales` 只在 campaign 层有），**不能纯靠"最细粒度 rollup"生成上层**——必须各自物化。这正是"分表"不可避免的根本原因。

### 阶段 3 · 上自助 BI 时，做真正的星型

```
dim_account / dim_campaign / dim_ad_group / dim_target / dim_placement / dim_product
        ↓
fact_ad_campaign_daily / fact_ad_placement_daily / fact_ad_targeting_daily / ...
     （每张表只带自己的维度列与指标列，主键清晰，可加 FK）
```

此时宽表降级为**纯 ODS**，只在 ETL 链路里存在，永不出现在 BI 语义层。

## 八、一句话给同事解释

> 这张表像个**万能工具箱**：什么都有，但你每次拿工具都得先问"这个锤子是砸钉子的还是砸墙的"。
> 它当仓库货架（ODS）挺好；当工作台（分析层）不行——因为**它不告诉你哪个口径是对的**。

## 附：复核 SQL（可直接粘贴执行）

```sql
-- ① 逐列逐层的填充率矩阵（一次性建张临时表，再逐列填）
CREATE TEMP TABLE col_cov AS
SELECT column_name,
       0 AS lv_campaign, 0 AS lv_placement, 0 AS lv_targeting,
       0 AS lv_advertised_product, 0 AS lv_purchased_product
FROM   information_schema.columns
WHERE  table_schema = 'core' AND table_name = 'ad_daily';

DO $$
DECLARE c record;
BEGIN
  FOR c IN SELECT column_name FROM information_schema.columns
           WHERE table_schema='core' AND table_name='ad_daily'
  LOOP
    EXECUTE format($f$
      UPDATE col_cov SET
        lv_campaign           = (SELECT count(%1$I) FROM core.ad_daily WHERE data_level='campaign'),
        lv_placement          = (SELECT count(%1$I) FROM core.ad_daily WHERE data_level='placement'),
        lv_targeting          = (SELECT count(%1$I) FROM core.ad_daily WHERE data_level='targeting'),
        lv_advertised_product = (SELECT count(%1$I) FROM core.ad_daily WHERE data_level='advertised_product'),
        lv_purchased_product  = (SELECT count(%1$I) FROM core.ad_daily WHERE data_level='purchased_product')
      WHERE column_name = %1$L
    $f$, c.column_name);
  END LOOP;
END $$;

-- ② 每个业务列被几层使用 + 覆盖率
SELECT column_name,
       (lv_campaign>0)::int + (lv_placement>0)::int + (lv_targeting>0)::int
     + (lv_advertised_product>0)::int + (lv_purchased_product>0)::int AS 被几层使用,
       lv_campaign, lv_placement, lv_targeting, lv_advertised_product, lv_purchased_product
FROM   col_cov
ORDER  BY 2, 1;

-- ③ 只看死列（0 层）与独占列（1 层）
WITH cov AS (
  SELECT column_name,
         (lv_campaign>0)::int + (lv_placement>0)::int + (lv_targeting>0)::int
       + (lv_advertised_product>0)::int + (lv_purchased_product>0)::int AS n
  FROM   col_cov
)
SELECT n AS 被几层使用, count(*) AS 列数,
       string_agg(column_name, ', ' ORDER BY column_name) AS 列清单
FROM   cov
WHERE  n <= 1
GROUP  BY 1 ORDER BY 1;

-- ④ 可加性反证（正确值 vs 错 4 倍）
SELECT (SELECT sum(spend) FROM core.ad_daily WHERE data_level='campaign') AS 正确值,
       (SELECT sum(spend) FROM core.ad_daily)                             AS 五层相加;

-- ⑤ 各层真实用到的列数
SELECT data_level, count(*) AS 行数,
       sum(CASE WHEN lv>0 THEN 1 ELSE 0 END) AS 该层用到列数
FROM (
  SELECT 'campaign' AS data_level, lv_campaign           AS lv FROM col_cov
  UNION ALL SELECT 'placement',          lv_placement          FROM col_cov
  UNION ALL SELECT 'targeting',          lv_targeting          FROM col_cov
  UNION ALL SELECT 'advertised_product', lv_advertised_product FROM col_cov
  UNION ALL SELECT 'purchased_product',  lv_purchased_product  FROM col_cov
) t GROUP BY 1 ORDER BY 1;
```

> 注：`format('%1$I')` 用 `I` 做标识符转义、`%1$L` 用 `L` 做字面量转义 —— 这里列名来自 `information_schema`，不是用户输入，但仍按规范转义。

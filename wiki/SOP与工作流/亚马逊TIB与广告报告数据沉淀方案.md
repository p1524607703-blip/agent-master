# 亚马逊TIB与广告报告数据沉淀方案

> [!summary] 摘要
> 亚马逊广告分析采用“小时级过程数据＋日级成熟结果＋TIB周期快照＋广告变更记录”四层体系。小时报告负责预算覆盖和时段结构，日级报告负责成熟购买、销售与ROAS，TIB只判断预算内覆盖时间；各表按稳定唯一键更新，不把重复导出简单相加。

## 核心知识

### 最近五个对话回合形成的决策链

以下按时间从早到晚整理：

| 回合 | 问题 | 已形成结论 |
|---|---|---|
| 1 | `XH1-W81女 自动-提高和降低-0.5` 从每日 $300 提到 $500 后，是否继续增加晚间预算 | 暂不增加。此前日均花费约 $146.52，远低于 $300，晚间缺量并非已证实的预算约束；先观察 8 月 3 日调预算后的 3–7 天日期×小时数据。 |
| 2 | ZJ1 运营下是否存在“看过 STV 后由 SD 追投”的活动 | `ZJ1-WK102 展示 VCPM AMC 多次PDP浏览 6.8` 确实出现在视频观看或点击后的路径中，但活动名更像“多次 PDP 浏览”受众；路径经过该广告不等于其定向条件就是 STV 观看者。 |
| 3 | 7 月 22 日至 8 月 4 日的 14 天滚动小时报告，哪些日期可用、多久获取一次 | 将流量过程窗口与成熟效率窗口分开；小时报告负责覆盖，日级报告负责最终 ROAS。最初建议每 3 天获取一次最新 14 天，最低每 7 天一次。 |
| 4 | 实际定期导出只能选择“最近 7 天”，本周和上周选哪个 | 选择“上周”。固定在每周五或周六导出完整上周，避免本周周期不完整、周末缺失和最新日期归因过浅。该限制取代了“每 3 天导出最新 14 天”的初始方案。 |
| 5 | Codex 如何做数据入库 | 当时初步建议 Python＋SQLite＋固定报告目录；现已根据后续需求调整为 PostgreSQL 主库，继续执行文件识别、清洗、去重更新、归档和异常汇总。 |

> [!warning] 当前有效的导出频率
> 在后台定期任务只能选择“最近 7 天／本周／上周”的前提下，当前采用的正式方案是：**每周五或周六导出“上周”**。此前“每 3 天获取最新 14 天”只适用于允许自由选择滚动 14 天区间的导出方式，不再作为当前自动任务的执行口径。

### 四类数据各自负责什么

| 数据层 | 推荐粒度 | 主要用途 | 不能单独证明什么 |
|---|---|---|---|
| 小时级广告活动报告 | 账户×广告产品×活动×日期×小时 | 展示、点击、花费、CPC、最后活跃小时、预算消耗曲线、跨日时段稳定性 | 未成熟日期的最终购买、销售和 ROAS |
| 日级广告活动报告 | 账户×广告产品×活动×日期 | 成熟购买、成熟销售、最终 ROAS、前后周期验证、产品线总量和内部迁移 | 具体哪个小时断流或高效 |
| TIB 广告活动报告 | 账户×活动×明确统计周期×导出版本 | 平均预算内活跃时间、预算覆盖候选筛选、周期性 TIB 快照 | 活动质量、断流后需求、增加预算一定有效 |
| 广告变更记录 | 活动×变更时间×变更类型 | 还原预算、竞价、动态策略、广告位和分时规则的实验条件 | 广告效果本身 |

正式 TIB 四象限要求 TIB 与分析用小时报告的统计周期完全一致；周期错位时只能展示 TIB，不能据此形成正式预算或竞价动作。

### 日期成熟度口径

假设文件导出日期为 `T`：

| 状态 | 日期规则 | 可使用指标 |
|---|---|---|
| 处理中 | `T` 当天、前 1 天或最近 48 小时 | 展示、点击、花费、活跃小时 |
| SP 归因回填中 | `T-3` 至 `T-7` | 过程趋势；购买、销售和 ROAS 标记为未锁定 |
| Seller SP 成熟 | `≤ T-8` | 购买、销售、CVR、ROAS |
| 14 天归因活动回填中 | `T-3` 至 `T-14` | 过程趋势；购买、销售和 ROAS 标记为未锁定 |
| SB、SD、STV 等成熟 | `≤ T-15` | 购买、销售、CVR、ROAS |

以 2026 年 8 月 5 日导出的 7 月 22 日至 8 月 4 日报告为例：

- 7 月 22 日至 8 月 2 日：可用于展示、点击、花费和小时覆盖分析；
- 7 月 22 日至 7 月 28 日：可作为 Seller SP 的成熟效率窗口；
- 7 月 29 日至 8 月 2 日：属于归因回填观察区；
- 8 月 3 日至 8 月 4 日：只做近期过程监控；
- SB、SD、STV：该 14 天小时报告内没有完整成熟窗口，应由更晚的日级报告锁定结果。

> [!note] 成熟状态的实现
> `report_exported_at` 必须保留。数据是否成熟应根据“统计日期＋广告产品＋最新报表导出时间”判断，而不能只看今天的日期。旧文件不会因为时间过去而自动补齐归因：当预计成熟日已到、但库内最新版本仍来自成熟日前的报表时，应标记为“需要刷新成熟版本”，直到导入一份成熟日之后重新生成的报告。

### 固定获取与验收节奏

| 时间 | 获取内容 | 使用方式 |
|---|---|---|
| 每周五或周六 | 完整“上周”的小时级广告活动报告 | 沉淀连续小时事实，分析覆盖、断流、花费和 CPC |
| 每周同一天 | 最新 TIB 广告活动报告，并记录明确统计起止日期 | 与相同周期的小时报告匹配，更新 TIB 候选 |
| **每月 16 日** | **上一个完整自然月的日级广告活动报告** | 作为月度成熟结果锁定版，统一覆盖 SP、SB、SD、STV 等广告类型 |
| 活跃实验期每周同一天（可选） | 最近 30–60 天的日级广告活动报告 | 通过重叠更新提前观察归因回填，不代替月度成熟锁定版 |
| 每次广告调整时 | 预算、竞价、动态策略、广告位、搜索词结构、Listing 条件和分时规则 | 建立可比基线，避免同时修改多个变量 |

调整后的判断分两次完成：

1. 第 7 天做过程验收：覆盖是否延长、目标时段是否获得流量、CPC 是否异常、预算是否更早耗尽；
2. 归因成熟后做结果验收：最终购买、销售、ROAS、产品线总量以及是否发生内部迁移。

#### 日级报告的月度导出规则

推荐固定为：

> **每月 16 日，按广告账户时区导出上一个完整自然月。**

这样上月最后一天在导出时已经达到 `T-15` 或更早，可统一满足 Seller SP 的 7 天归因口径和 SB、SD、STV 等 14 天归因口径。虽然仅分析 Seller SP 时每月 9 日左右即可导出，但为避免按广告类型维护两套任务，统一使用每月 16 日更稳妥。

示例：

| 执行日期 | 导出区间 |
|---|---|
| 2026-09-16 | 2026-08-01 至 2026-08-31 |
| 2026-10-16 | 2026-09-01 至 2026-09-30 |

如果自动任务不能选择“上一个自然月”，只支持滚动区间，则每月 16 日导出**最近 60 天**，入库后按日期筛选并锁定上一个自然月；重叠数据继续使用较新导出版本 Upsert。

### 活动命名与运营/产品线判定规则（2026-08-13）

- **现状（代码实现，amazon-ads-data/src/amazon_ads_data/parsers.py）**：`product_line_from_name()` 按 `-` 拆分活动名后**取前两段**拼接（如 `XH1-W8K6-shoes-广泛-…` → `XH1-W8K6`）；`owner_name` 无自动解析，由 CLI/MCP 显式传入（`--owner`，默认 panjinlong），存的是名称**第一段代号**。
- **已知缺陷（库内实证）**：core 表 product_line 存在大量脏值，如 `XH1-W81女 视频`、`DD1-S81 展示`、`XH1-W8K6 头条`、`XM1-Y10 视频出单词精准`、`ZF1-W882男 展示型`——因名称第二段含空格或"空格+投放类型后缀"未按 `-` 分隔；`managed_campaigns` 里的 product_line 是干净精确值（显式传入，非自动解析）。
- **已出现的运营代号**：WHITIN 账户 = ZJ1 / XH1 / ZF1 / LB1 / DD1 / YT1；欧德思账户 = XM1 / XM2。**代号→运营人名的映射表尚未建立**，需要用户补充。

建议至少维护以下表：

| 表 | 作用 | 推荐唯一键 |
|---|---|---|
| `import_batches` | 文件名、SHA256、报告周期、导出/导入时间、行数、状态和错误 | 文件 SHA256 |
| `campaign_hourly` | 小时级活动事实 | 账户 ID＋广告产品＋活动 ID＋日期＋小时 |
| `campaign_daily` | 日级成熟结果 | 账户 ID＋广告产品＋活动 ID＋日期 |
| `campaign_tib_snapshot` | TIB 周期快照与预算、策略、状态 | 账户 ID＋活动 ID＋报告起止日期＋导出时间 |
| `campaign_change_log` | 广告调整与实验记录 | 变更记录 ID |
| `campaign_product_line_mapping` | 活动到产品线的人工覆盖映射 | 账户 ID＋活动 ID |
| `campaign_watchlist` | 记录本人负责、需观察或已移交的活动及复查周期 | 账户 ID＋活动 ID |
| `campaign_review_log` | 记录每次复查、判断、建议动作和下一次复查时间 | 复查记录 ID |

入库原则：

- 同一文件用 SHA256 防止重复导入；
- 同一业务唯一键收到更新的导出版本时执行 Upsert，不重复累加；
- 只有 `report_exported_at` 更新的版本才能覆盖旧版本，防止旧文件反向覆盖新数据；
- `campaign_id`、`account_id` 等长 ID 保存为文本；
- 空白、`-`、`—`、`N/A` 保存为 `NULL`，不自动改成 0；
- ROAS 使用 `SUM(sales) ÷ SUM(spend)` 重算，不平均行级 ROAS；
- 原始文件进入归档目录，批次表保留来源和导入审计；
- 如需分析归因回填速度，可在“当前事实表”之外保留版本快照；正式分析默认读取最新版本。

#### 成熟度字段与刷新判断

`campaign_hourly` 和 `campaign_daily` 至少保留：

| 字段 | 用途 |
|---|---|
| `stat_date` | 数据所属自然日 |
| `ad_product` | 决定使用 7 天还是 14 天归因口径 |
| `latest_report_exported_at` | 当前事实值来自哪一次报告导出 |
| `attribution_window_days` | SP 默认 7，SB、SD、STV 等默认 14 |
| `mature_after` | SP 为统计日后第 8 天，14 天归因活动为统计日后第 15 天 |
| `attribution_status` | `processing`、`backfilling` 或 `mature` |

另建查询视图 `v_attribution_refresh_due`：

- 今天尚未到 `mature_after`：继续等待；
- 今天已到 `mature_after`，但 `latest_report_exported_at` 早于 `mature_after`：标记 `needs_refresh`；
- 最新报表导出时间已达到成熟日：标记 `mature`。

这样既能分析近期数据，也不会把旧文件中的阶段性购买和销售误当作成熟结果。

#### 三种分析模式

| 模式 | 数据范围 | 允许形成的判断 |
|---|---|---|
| 近期过程 | 最近 48 小时以外的最新完整过程数据 | 展示、点击、花费、CPC、活跃小时和异常趋势；ROAS 标注未锁定 |
| 归因回填观察 | 已超过 48 小时但尚未成熟 | 观察购买、销售和 ROAS 方向，不做最终定性 |
| 成熟结果 | 最新导出版本已达到成熟日 | 正式 ROAS、四象限、动作成败和产品线增量验收 |

#### 本人负责活动与定期跟进

`campaign_watchlist` 建议字段：

| 字段 | 含义 |
|---|---|
| `account_id`、`campaign_id` | 稳定关联广告事实表 |
| `campaign_name`、`ad_product`、`product_line` | 展示和归类 |
| `owner` | 当前负责人 |
| `responsibility_status` | `owned`、`watching`、`handed_off`、`closed` |
| `priority` | 高、中、低 |
| `review_frequency_days` | 常规复查周期 |
| `last_reviewed_at`、`next_review_at` | 上次与下次复查时间 |
| `target_roas` | 产品线或活动目标 ROAS |
| `followup_reason` | 预算覆盖、竞价测试、流量质量、成熟结果等待等 |
| `last_notified_at`、`snooze_until` | 防止重复提醒并支持暂缓 |
| `active`、`notes` | 是否仍需跟进及补充说明 |

`campaign_change_log` 还应增加：

- `process_review_due_at`：通常为动作后第 7 天；
- `mature_review_due_at`：根据广告产品与测试结束日计算；
- `expected_outcome`：本次动作希望改变什么；
- `rollback_condition`：达到什么条件需要回退；
- `review_status`：待过程复查、待成熟复查、已验证、已回退。

创建视图 `v_campaign_review_due`，合并 `campaign_watchlist`、`campaign_change_log` 和最新事实数据，输出：

```text
负责人
广告活动
复查原因
到期时间
最新数据日期
成熟状态
最近7天花费、购买和ROAS
上次动作
建议复查类型
```

提醒任务只查询以下对象：

- `next_review_at` 已到期的本人负责活动；
- 动作后第 7 天需要过程验收的活动；
- 已到成熟复查日且成熟版本已经入库的活动；
- 已到成熟复查日但仍缺成熟版本、需要重新获取报告的活动；
- 最新数据过旧或导入失败的活动。

#### 文件扫描与提醒任务

推荐由一个本地定期任务每日扫描一次，而不是常驻监听：

```text
扫描 incoming
→ 计算文件哈希并排除已导入文件
→ 根据列名识别小时级、日级或TIB报告
→ 校验后在事务内Upsert
→ 成功归档，失败隔离并记录原因
→ 更新成熟刷新视图和活动复查队列
→ 只在有新文件、导入失败或有复查到期时通知
```

报告按周或按月生成时，每日扫描一次已经足够。正式创建任务前需要确认：

1. 报告实际下载到哪个本地文件夹；
2. PostgreSQL 是运行在本机、NAS、公司服务器还是云数据库；
3. 每天希望几点扫描；
4. 提醒只显示在 Codex 当前任务，还是还需要同步到其他渠道。

#### PostgreSQL、BlazeSQL与Codex的连接边界

推荐架构：

```text
亚马逊报告
→ 本地入库程序
→ PostgreSQL主库
├→ BlazeSQL：自然语言查询、图表和看板
└→ Codex只读连接：定期分析、知识沉淀和到期提醒
```

BlazeSQL 可以连接 PostgreSQL、理解数据库结构、生成并执行 SQL，再把结果展示为表格、图表或看板。但在电脑上安装 BlazeSQL 并不会自动授权当前 Codex 任务访问数据库：

- BlazeSQL 桌面端是独立的分析界面；
- 当前 Codex 任务需要单独的本地只读连接、MCP 服务或受控查询 API；
- 如果使用 BlazeSQL 提供的数据库连接 API，也需要额外配置访问凭据和权限；
- BlazeSQL 桌面离线模式下，查询结果默认留在本机，因此不会自动同步给外部 ChatGPT/Codex；
- BlazeSQL Web 模式会把查询结果加密存储到其云端，启用前需要单独评估公司数据合规要求。

PostgreSQL 建议划分三个角色：

| 角色 | 权限 |
|---|---|
| `ads_ingest` | 只负责批次表和广告事实表的导入、更新与归档状态 |
| `ads_analyst` | 只读分析视图，供 BlazeSQL 和 Codex 查询 |
| `ads_operator` | 只允许维护负责活动、动作记录、复查记录和提醒状态 |

BlazeSQL 和 Codex 不应使用数据库管理员账户，也不应直接获得事实表的删除权限。对外只暴露经过定义的分析视图：

- `analytics.v_campaign_recent`：近期过程数据，ROAS 标注未锁定；
- `analytics.v_campaign_mature`：仅使用成熟版本；
- `analytics.v_campaign_review_due`：本人负责且已到复查时间的活动；
- `analytics.v_attribution_refresh_due`：已到成熟日但缺新版报告的数据；
- `analytics.v_import_health`：最近导入时间、失败批次和数据缺口。

BlazeSQL 负责交互式问答和看板；Codex 负责按 TIB 规则复核、把结论写入知识库，并通过定期任务查询到期视图。两者使用同一 PostgreSQL 数据源，但职责不同。

### TIB 动作判断的关键护栏

- 低 TIB 只说明预算内覆盖时间短，不代表广告表现好，也不证明断流后有可盈利需求。
- 日均花费远低于预算时，晚间缺流量优先检查竞价、相关性、搜索量、搜索词和广告资格，不继续增加预算。
- 预算解决“能否继续参与”，竞价解决“能否赢得拍卖”，两者分开测试。
- 路径数据观察到“STV 后经过 SD”只能证明触点顺序，不能证明 SD 的受众定义就是 STV 观看者。
- 单活动订单增加必须同时检查同产品线其他活动和产品线总量，防止把内部迁移误判为真实增量。

### 分阶段实施

1. **阶段一**：PostgreSQL＋每周小时报告＋批次哈希＋唯一键 Upsert＋产品线映射；
2. **阶段二**：增加日级成熟报告、TIB 周快照、广告变更记录、负责活动表和前后周期对比；
3. **阶段三**：BlazeSQL 使用只读角色连接分析视图，完成自然语言查询和看板；
4. **阶段四**：为 Codex 增加本地只读桥接与定期任务，自动生成到期活动清单和复查报告。

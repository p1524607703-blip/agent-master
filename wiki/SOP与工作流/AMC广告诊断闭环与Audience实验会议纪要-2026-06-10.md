# AMC广告诊断闭环与Audience实验会议纪要-2026-06-10

> [!summary] 摘要
> 会议明确将当前 AI 广告分析从一次性报表解读升级为“数据清洗、诊断、人工执行、结果回传、周期复盘”的闭环。短期优先完成搜索词/否词 Skill、Rule-based Audience 对照实验和权限治理，Lookalike、订阅标签与自动执行均需先验证。

## 核心知识

### 核心决策

| 决策 | 会议结论 | 当前边界 |
|---|---|---|
| 广告诊断闭环 | 数据导出、清洗、AI 分析、人工执行、结果回传、再次分析形成循环 | 毛利、预算、库存尚未纳入 |
| 分析粒度 | 优先按一个产品及其多个广告活动分析 | 整账号数据过大，容易漏读 |
| 效果验证 | 比较优化前后 ACOS、CVR、ROAS，并记录建议采纳情况 | 试点时间尚不足 |
| 自动化顺序 | 先验证建议有效，再标准化并生成批量操作表 | 暂不自动改价、否词或预算 |
| Audience 路线 | 优先测试 Rule-based，Lookalike 单独做扩量实验 | 小池子跑不动，宽池子预算风险高 |
| 产品化 | 先做搜索词诊断、否定词建议和执行回传 | SQL 功能必须区别于 AMC 后台 |
| 权限 | 技术侧负责读取、分析和建议，运营负责写操作 | 生产账号写权限需隔离 |

### AI 广告诊断闭环

```mermaid
flowchart LR
    A[导出广告与 AMC 数据] --> B[清洗与聚合]
    B --> C[AI 诊断与 Audience 假设]
    C --> D[运营人工复核]
    D --> E[执行否词 调价或实验]
    E --> F[回传执行动作与结果]
    F --> G[7 30 90 天复盘]
    G --> C
```

- 运营面对长报表时，容易只看高频大词，忽略中等频率但长期浪费的搜索词。
- 当前交付是一份分析报告和一份清洗后的 Excel；理想状态是将执行动作和结果回传为 Excel/JSON。
- 一个产品可能包含多个广告活动，适合成组分析；整账号一次性输入会增加数据噪声。
- 评价逻辑不能只看统一 ACOS 阈值，还应考虑产品阶段、投放目标、毛利、预算和库存。
- 数据窗口建议同时保留 7 天、30 天和 90 天，先聚合再交给模型解释趋势。

### Measurement 与 Audience

| 类型 | 定位 | 用途 |
|---|---|---|
| Measurement | 匿名聚合报表 | 规模估算、路径、频次、曝光与效果分析 |
| Audience | 可激活人群包 | 用于广告测试，不导出用户明细 |

> [!warning] 频次口径待确认
> 高触达次数对应更低 ACOS 时，必须先确认 Spend 是否包含此前全部触点成本，否则不能据此判断最佳触达频次。

### Audience 能力边界

| 需求 | 会议判断 | 状态 |
|---|---|---|
| 搜索关键词、广告点击、PDP 浏览、加购未购 | 多数可组合 | 可测试 |
| 页面停留 30 秒 | 当前没有明确事件字段 | 暂不可做 |
| 竞品 ASIN 浏览人群 | 多次尝试无结果，可能受账号边界限制 | 待验证 |
| 多广告重叠人群及差集 | 可用于重投或排除重复高成本人群 | 可设计实验 |
| 跨账号复用 SQL | 可能因账号触达历史产生不同结果 | 必须验证 |
| 地域缩小 Lookalike | 投放界面可能支持 Location，查询层不明确 | 待验证 |

### Rule-based 与 Lookalike

- Rule-based 更精准，但常只有几千或更少，可能跑不出足够曝光和转化。
- Lookalike 可快速扩量，但“最相似”档位也可能显示约 99 万；该数值可能是显示上限，而非真实精确人数。
- 复杂规则叠加小样本时，扩展算法不可解释，不能默认仍保留原规则的业务含义。
- 会议倾向：复杂高意向条件先用 Rule-based，Lookalike 作为独立扩量实验。

### 订阅标签数据

会议查看了 In-market、Lifestyle、兴趣/人生阶段及区域类数据源。这些数据本质上是亚马逊官方受众标签，可与广告行为交叉分析。

| 标签方向 | 可能用途 | 当前判断 |
|---|---|---|
| In-market | 关键词、类目、商品定位 | 优先级高，但颗粒度可能偏粗 |
| Lifestyle | 视频素材和场景脚本 | 正在跑数 |
| 兴趣标签 | SD 视频、DSP 或扩量 | 需结合重叠率和投放验证 |
| 人生阶段/年龄 | 补充画像 | 优先级较低 |

### Hermes 产品化方向

- 前端价值是固化多步骤流程，减少漏步骤、走偏和错误结果。
- P0：上传数据，输出搜索词诊断、否定词候选、确定执行项和人工审核项。
- P0：记录执行回传，并自动形成下一轮分析输入。
- P1：广告触点分析、Audience 模板和跨账号边界验证。
- P2：扩词、新词发现、API 自动跑 SQL 和批量操作表。
- 若 AMC 后台已提供同等可视化能力，Hermes 必须在批量处理、规则复用、实验管理或结果回传上形成差异。

### GPT建议

> [!note] GPT建议 1：定位
> 将 Hermes 定位为“广告决策与实验系统”，而不是自动投放系统。先串起假设、数据、建议、人工决策、执行结果和复盘，再逐步开放自动执行。

> [!note] GPT建议 2：三层输出
> 每次分析固定输出“事实、判断、行动”三层，判断需标注置信度和依赖假设，行动需包含观察周期与停止条件。

> [!note] GPT建议 3：实验预注册
> 创建 Audience 前写清产品、假设、测试组、对照组、预算上限、主指标、停止条件和外部变量。复盘同时看 ACOS、CVR、ROAS、花费、触达人数和增量订单。

> [!note] GPT建议 4：Audience 状态机
> 使用 `TOO_SMALL`、`READY_FOR_TEST`、`TOO_BROAD`、`FIELD_UNAVAILABLE`、`ACCOUNT_DEPENDENT` 等状态，避免把所有人群都直接送入投放。

> [!note] GPT建议 5：权限与审计
> 能力拆成 Read、Propose、Execute 三层。提示词、模型版本、输入文件、建议、人工确认和最终动作均保留审计记录。

### 待验证清单

- [ ] 频次分析中的 Spend 是否包含完整触点成本。
- [ ] 同一份 Audience SQL 在两个账号中的规模和结果是否一致。
- [ ] 竞品 ASIN、搜索关键词、地域字段的数据边界。
- [ ] 页面停留时长是否存在可用事件。
- [ ] “99万”是显示上限、档位上限还是实际人数。
- [ ] Location 能否在 Audience 查询层缩小池子。
- [ ] 一个广告活动或广告组可绑定的人群包数量。
- [ ] 亚马逊官方搜索词报告的准确名称、入口和周期。
- [ ] 付费订阅标签数据的实际增量价值。

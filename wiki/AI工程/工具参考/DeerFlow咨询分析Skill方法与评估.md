# DeerFlow 咨询分析 Skill 方法与评估

> [!summary] 摘要
> `consulting-analysis` 是 ByteDance DeerFlow 2.0 内置的咨询报告编排 Skill。它不负责采集数据，而是先生成可执行的研究框架和数据需求，再接收其他工具返回的数据包，产出带图表、对比表、战略洞察与引用的咨询级报告。其核心价值是“框架—采数—报告”的职责分离与明确交接；落地时仍需补强证据账本、推断等级、数据质量校验和篇幅弹性。

## 核心知识

### 1. 所处系统与定位

- DeerFlow 2.0 是基于 LangGraph 和 LangChain 的长任务 SuperAgent harness，组合文件系统、长期记忆、沙箱、工具、Skills 与子 Agent。
- DeerFlow 将 Skill 定义为以 `SKILL.md` 为核心的结构化能力模块，并按任务需要渐进加载。
- `consulting-analysis` 位于 `skills/public/consulting-analysis/SKILL.md`，是一个公开的工作流规范，不是独立程序，也不是数据源。
- 同一公共目录还提供 `deep-research`、`data-analysis`、`chart-visualization` 和 `ppt-generation` 等 Skill；`consulting-analysis` 的设计意图就是与这些采集、分析、制图和交付能力组合使用。
- 它覆盖市场分析、消费者洞察、品牌分析、财务分析、行业研究、竞争情报和投资尽调等场景，默认输出中文 Markdown。
- 文件历史显示：2026-02-12 首次整合市场/数据分析与图表可视化，2026-02-25 增强数据真实性协议和报告规范。

### 2. 两阶段工作流

```text
研究主题与范围
    ↓
Phase 1：分析框架
    ↓ 输出章节骨架、数据需求、检索词、优先级、图表计划
外部采数与制图 Skill
    ↓ 输出 Data Summary、Chart Files、External Search Findings
Phase 2：报告生成
    ↓
咨询级 Markdown 报告
```

| 阶段 | 核心输入 | 核心动作 | 核心输出 |
|---|---|---|---|
| Phase 1 | 研究主题；可选范围、限制与特定角度 | 识别分析域，选择框架，设计章节，定义数据和可视化需求 | Analysis Framework、Data Collection Task List |
| 中间交接 | Analysis Framework | 由其他 Skill 执行检索、采数、核验与制图 | Data Summary、Chart Files、External Search Findings |
| Phase 2 | Analysis Framework + Data Summary；图表与搜索发现可选 | 校验 P0 数据，先生成图表，再按证据组织章节 | 最终咨询报告与参考文献 |

> [!warning] 能力边界
> 该 Skill 明确声明自己**不执行数据采集**。单独使用只会得到研究框架，或基于现成数据包写报告；完整运行必须编排搜索、数据分析、图表生成等其他能力。

### 3. Phase 1：把研究问题变成可执行任务

1. 识别研究对象和分析域，并映射自然分析维度。例如市场分析关注规模、增速、细分、驱动因素、竞争和消费者；财务分析关注宏观、行业、基本面、估值和风险。
2. 从经典框架中选择 2–4 个互补且数据可得的方法，如 PESTEL、波特五力、SWOT、TAM-SAM-SOM、RFM、消费者决策旅程等。强调深度优先于框架数量，并要求框架显式映射到章节。
3. 每章定义标题、分析目标、分析逻辑和待验证的核心假设。
4. 每章列出具体数据指标、数据类型、建议来源、检索关键词、P0/P1/P2 优先级和时间范围，形成下游 Agent 可直接执行的数据契约。
5. 同时规划图表类型、数据映射、对比表结构，以及 `What → Why → So What` 的论证链。
6. 将所有 P0/P1 数据需求汇总、去重，形成统一采数清单。

### 4. Phase 2：把数据包变成报告

- 先检查分析框架、Data Summary 和图表路径，逐项核对 P0 数据；缺失时必须显式标注。
- 在写正文前集中完成所有图表；无法生成图表的章节用对比表作为视觉锚点。
- 每个子章节遵循“视觉证据 → 数据对比 → 综合分析”的顺序，正文用 `What → Why → So What` 解释数据。
- 洞察链被定义为“数据 → 用户心理 → 策略含义”，章节末可用一句话结论收束。
- 最终结构固定为摘要、引言、主体章节、结论、参考文献；正文中使用 Markdown 链接，文末参考文献要求采用 GB/T 7714-2015。

### 5. 数据真实性约束

- 报告数据和图表只能来自 Data Summary 或 External Search Findings。
- 禁止发明、估算、模拟或为了图表观感而平滑数据；缺失信息写明不可得。
- 主要观点和图表必须能追溯到输入数据包。
- 数字表格和叙述均不得超出已提供证据，P0 数据缺失必须告知用户。

### 6. 方法评价

#### 值得借鉴

- **职责分离清晰**：研究设计、数据采集和报告写作不混在同一步，便于长任务交接与失败恢复。
- **数据契约具体**：把“需要更多数据”细化为指标、来源、检索词、优先级和时间范围，可直接转成任务队列。
- **框架与证据绑定**：要求所选分析框架必须数据可得，并映射到具体章节，降低只堆模型名称的问题。
- **图文叙事一致**：先定义图表和对比结构，再组织论点，适合市场调研、竞品分析和管理层汇报。
- **内置验收清单**：两阶段都有质量检查，对长报告的一致性和完整性有帮助。

#### 需要改造

- **证据追踪还不够细**：虽然强调可追溯，但未强制每条 Data Summary 记录携带 `source_id`、原始链接、发布日期、抓取日期和证据等级。建议增加 Evidence Ledger，并让每个数字和主张引用证据编号。
- **心理推断容易越界**：仅凭占比或 TGI 不能自动推出审美、社交认同等心理动机。“数据 → 用户心理”应改为“数据 → 可观察行为 → 有证据支持的动机假设 → 策略”，并标注事实、推断、假设三级。
- **缺少系统数据质量检查**：应增加口径统一、样本代表性、时间窗口、币种与单位、重复数据、异常值、冲突来源和三角验证。
- **固定每节至少 200 词会鼓励注水**：应按决策价值和证据密度控制长度，管理层摘要和数据不足章节不应为满足字数而扩写。
- **图表先行过于刚性**：可保留先规划图表，但正式出图前应先做数据覆盖率和图表适配检查；数据不足时应允许取消或替换图表。
- **“麦肯锡/BCG 语气”只是风格约束**：专业质量更依赖问题定义、MECE 结构、证据强度、替代解释和建议的可执行性，不能由语气替代。
- **建议缺少执行闭环**：可补充建议的负责人、优先级、成本、预期影响、前置依赖、风险、验证指标和停止条件。

### 7. 对当前知识库的适配建议

结合本库的三层架构，建议把该方法改成四段式工作流：

1. **研究简报**：明确决策问题、范围、对象、时间、成功标准和不可回答项。
2. **框架与数据契约**：生成章节骨架、核心假设、P0/P1/P2 数据清单、证据标准和可视化计划。
3. **采集与证据账本**：原始资料进入 `raw/`，结构化记录 `source_id`、来源类型、发布日期、抓取日期、指标口径、证据等级和冲突说明。
4. **分析与交付**：最终报告进入 `wiki/`，正文区分事实、推断和建议；建议附行动优先级、指标和验证周期。

对跨境电商场景，不建议照搬通用框架库，而应优先接入已有的亚马逊搜索词、品牌分析、广告报表、竞品 Listing、评论和类目数据工作流。`consulting-analysis` 更适合作为“研究总编排 + 最终报告规范”，而不是替代已有采数 Skill。

# 知识库架构诊断报告 — Karpathy 方案对照分析

## 一、架构层面对比

Karpathy 提出核心洞察：**"RAG 是按次计费，Wiki 是复利资产"**。他的方案建立在严格的三层分离之上。对照你的知识库，差距如下：

| Karpathy 三层 | 你的对应层 | 差距 |
|---|---|---|
| **raw/** — 原始素材，只读不改 | ❌ 不存在 | 所有资料没有"只读源"概念，原始素材和加工产物混在一起 |
| **wiki/** — AI 维护的结构化知识 | `01-产品/`、`02-AI工程/`、`03-知识库/` 等 | 有分类意识，但无统一页面格式、无自动关联规范、无 AI 维护流程 |
| **AGENTS.md** — 规则说明书 | `CLAUDE.md`（210 行） | 当前定位是**项目基础设施文档**，而非**知识管理宪法** |

**结论**：你的库有 PARA 分类法的影子，但缺少 Karpathy 架构中最关键的两个概念——**原始资料与知识产物的物理隔离**，以及**给 AI 的知识管理操作规则**。

## 二、10 个具体问题

### 问题 1：没有 raw/ 与 wiki/ 的分离

**现状**：`01-产品/` 下同时存在原始调研数据（如 `果冻凉鞋-市场调研分析.md`）和加工后的交付物（如 `乐福鞋A+页面方案.md`）。AI 无法区分"这是源材料，只读" 和"这是我要维护的知识页"。

**后果**：AI 可能误修改原始资料；新资料摄入时，AI 不清楚该从哪里读、读完后输出到哪里。

**Karpathy 的做法**：
```
my-wiki/
├── raw/          ← 文章、报告、PDF 丢进来，永不修改
│   ├── 果冻凉鞋调研原文.md
│   └── amazon-aplus-spec-2026.pdf
├── wiki/         ← AI 生成和维护的知识页面
│   ├── 果冻凉鞋.md
│   └── 亚马逊A+页面规范.md
└── AGENTS.md     ← 规则
```

### 问题 2：CLAUDE.md 定位偏差（最关键）

**现状**：你的 CLAUDE.md 是一份优秀的**项目技术文档**——它详细描述了仓库包含什么、工具怎么用、选品工具的技术栈、后端架构、Prisma 模型等。但它**不是知识管理规则**。

Karpathy 的 AGENTS.md 核心内容应该包括：
- 文件夹规则（raw 只读、wiki AI 写）
- 页面格式规则（摘要 → 核心知识 → 关联链接 → 来源引用）
- 工作流规则（Ingest / Query / Lint 的具体操作步骤）
- 索引维护规则（何时更新 INDEX.md、何时追加 log.md）

**你的 CLAUDE.md 缺少的**：
- ❌ 没有定义"摄入新资料"的标准流程
- ❌ 没有规定知识页面的标准格式
- ❌ 没有交叉引用的强制性要求
- ❌ 没有矛盾检测和健康检查流程
- ❌ 没有 INDEX.md / log.md 的维护规则

### 问题 3：缺乏索引和日志系统

**现状**：有 `Daily/` 日记、有 `TikTok文档分类索引-2026-03-30.md`，但没有全局性的 wiki 索引和变更日志。

**Karpathy 标配**：
```
logs/
├── index.md    ← 所有 wiki 页面的目录，每个条目一行描述
└── log.md      ← 按时间倒序记录每次知识库变更
```

这两份文件是 AI 回答问题时"知道自己有什么知识"的关键入口。没有它们，AI 每次都要扫描整个文件树。

### 问题 4：知识页面格式不统一

**现状**：同样是产品分析文档——
- `WHITIN乐福鞋-产品分析.md` 结构自由
- `果冻凉鞋-市场调研分析.md` 结构不同
- `Amazon运动鞋品牌销量排名.md` 又是另一种结构

**Karpathy 的标准格式**：
```markdown
# 主题名
> 一段 200 字内核心摘要

## 核心知识点
- 要点 1
- 要点 2

## 关联主题
- [[相关主题A]]
- [[相关主题B]]

## 来源
- raw/xxx.md
```

### 问题 5：根目录极度杂乱

**现状**：根目录下有 20+ 张 `Pasted image *.png`、散落的 `.md` 文件（如 `ailyskill-DeepSeek-AI分析.md`、`2026-04-16.md`）、二进制文件（`go2rtc.exe`、`go2rtc_linux`）、压缩包。

**Karpathy 的原则**：知识库的根目录应该极简——只有 `raw/`、`wiki/`、`logs/`、`AGENTS.md` 和 `.obsidian/`。图片归属到对应页面所在的文件夹，临时文件不进库。

### 问题 6：存在重复知识结构

**现状**：
- `01-产品/TikTok广告工作流/` ↔ `ai研发+电商数据知识库/01-跨境电商/01-产品/TikTok广告工作流/`
- `01-产品/市场调研/` ↔ `ai研发+电商数据知识库/01-跨境电商/01-产品/市场调研/`
- `03-知识库/跨境电商/` ↔ `ai研发+电商数据知识库/01-跨境电商/知识库/`

**后果**：同一份知识有两个物理副本，更新 A 需要同步更新 B。AI 引用时可能拿到过期版本。这是知识管理的致命反模式。

### 问题 7：非知识制品混入知识库

**现状**：Obsidian vault 里包含：
- 完整的前后端项目源码（`选品工具/backend/src/`、`frontend/`、`dist/`）
- 二进制文件（`.exe`、`.zip`）
- Node 模块配置文件（`package.json`、`tsconfig.json`）
- 数据库文件（`dev.db`）

**建议**：软件项目应该独立于知识库之外管理。Obsidian vault 应仅包含 Markdown 笔记和附件（图片/PDF）。代码项目用专门的 Git 仓库。

### 问题 8：缺少健康检查（Lint）流程

**现状**：没有任何自动化或半自动化的知识库巡检机制。

**Karpathy 的 Lint 操作**：定期让 AI 检查——
- 是否有互相矛盾的旧观点
- 是否有"孤儿页面"（没有任何其他页面链接到它）
- 是否有提到但没有专属页面的概念
- 是否有过时信息

你的 `self-improving-agent` skill 已经具备了错误记录能力（`.learnings/ERRORS.md`），可以扩展为知识库级别的体检。

### 问题 9：收集箱 ≠ raw 入口

**现状**：`00-收集箱/收集箱.md` 是一个任务/想法快速倾倒区，风格是 GTD inbox。这很好，但它不是 Karpathy 意义上的 raw 资料入口。

**区别**：
- GTD 收集箱：放的是待处理事项，处理完就移走
- Karpathy raw/：放的是**永久保留的原始资料**，永远不改，AI 反复引用

两者可以共存，但不能混淆。

### 问题 10：交叉引用（Wikilinks）使用不系统

**现状**：部分文件使用了 `[[wikilinks]]`，但整体上没有形成系统性的知识图谱。很多文件是孤岛状态。

**Karpathy 的要求**：AI 在创建/更新每个 wiki 页面时，必须主动查找并链接到所有相关的已有页面。这是知识网络"越长越密"的关键。

## 三、CLAUDE.md 改进方案

你当前的 CLAUDE.md 是**基础设施说明**，它仍然有价值，但应该拆分为两部分：

### 改造方案：拆分为两个文件

```
agent-master/
├── CLAUDE.md          ← 保留，精简为项目技术指南（工具、技术栈、环境）
├── AGENTS.md          ← 新建，按 Karpathy 模式编写知识管理规则
```

**CLAUDE.md（精简后的技术指南）**：
- 仓库类型说明
- 已安装 CLI 工具
- AI 服务配置
- 选品工具项目的开发命令
- Skills 列表

**AGENTS.md（知识管理规则）**：
- 三层架构规则
- Ingest / Query / Lint 工作流
- 页面格式标准
- 索引和日志维护规则

### 建议的 AGENTS.md 模板

下面是一份针对你知识库定制的 AGENTS.md 模板，可以直接使用：

```markdown
# AGENTS.md — 知识管理规则

## 三层架构

本知识库采用 Karpathy 三层架构：

```
├── raw/                     ← 原始素材层（你提供，AI 只读不改）
├── wiki/                    ← 结构化知识层（AI 全权维护）
│   ├── 跨境电商/
│   ├── AI工程/
│   ├── 个人成长/
│   └── SOP工作流/
├── logs/
│   ├── INDEX.md             ← 所有 wiki 页面的目录
│   └── LOG.md               ← 变更日志（按时间倒序）
└── AGENTS.md                ← 本文件
```

### raw/ 规则

- 存放所有原始资料：文章、PDF 转录、报告原文、数据快照
- **只读、永不修改**
- 按来源分类：`raw/论文/`、`raw/网页/`、`raw/报告/`
- 文件名保留原始信息，不加整理

### wiki/ 规则

- AI 全权维护，人工只审核不编辑
- 每个主题一个页面，文件名使用中文
- 页面必须包含：
  1. 顶部：一段 200 字内核心摘要（`> [!summary]`）
  2. 中间：核心知识点（分点、表格、结构化）
  3. 底部：`## 关联` — [[wikilinks]] + `## 来源` — raw/ 路径
- 使用 `[[主题名]]` 主动关联相关页面

### 三大操作

#### Ingest（摄入）
当 raw/ 有新资料时：
1. 读取 raw/ 中的新文件
2. 在 wiki/ 创建或更新相关知识页面
3. 更新 logs/INDEX.md 中的目录条目
4. 在 logs/LOG.md 顶部追加本次操作记录

#### Query（查询）
当用户提问时：
1. 先读 logs/INDEX.md 了解有哪些知识
2. 定位相关 wiki 页面
3. 综合回答，附引用来源
4. 如果答案有长期价值，保存为新 wiki 页面

#### Lint（健康检查）
每月一次或在用户要求时：
1. 扫描 wiki/ 所有页面
2. 找出：矛盾观点、内容缺口、孤儿页面（无入链）、过时信息
3. 列出修复清单并逐项修复
4. 更新 logs/LOG.md

### 格式标准

- 使用 Obsidian Flavored Markdown
- `[[wikilinks]]` 必须用于所有页面间引用
- 中文内容、中文文件名
- 代码块标注语言
- 调用块使用 `> [!note]` 等标准格式
```

## 五、一句话总结

你的知识库在**内容丰富度**和**工具链成熟度**上远超大多数人的 Obsidian vault，但问题出在 **架构层面**：

- 有"文件夹分类"，没有"源/产分离"
- 有"CLAUDE.md"，没有"知识管理宪法"
- 有"Skills 自动化"，没有"Ingest → Wiki → Lint"的闭环

补齐 AGENTS.md + raw/wiki/logs 三层结构，你的知识库就能从"好用的笔记仓库"升级为"AI 帮你持续复利的知识系统"。

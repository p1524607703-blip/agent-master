## 四、分板块详情

### 4.1 广告数据中台（【A·数据与系统】）

**已完成**
- 数据库**已搭好并接入控制台**，后端是 **FastAPI**（"比较快一点的 Python 代码写的"），**基本由 AI 维护**。
- 业务映射链条已理清：**子ASIN → 父ASIN → 运营组**。
  - 其中 **子ASIN → 运营组** 是**唯一可确定**的边，能干净地区分出对应关系。
  - 仍有零星分不清的（举例：**W2030** 这类 ASIN）在慢慢调整 —— ⚠️ 与本地已知的 `B0DTK7FK2M` 被 1 条自指错标行污染成 `mixed_parent` 的问题**高度疑似同一件事**，值得核对。
- **CPO 计算**：按广告类型分类后计算，对数据库脚本来说压力不大。

**关于分组表的口径决定（重要）**
- A 建议：**不要自己再建一套分组表**，直接用公司**现有绩效系统**里已有的那张表 → 已拍板。
- 原因链：运营自己创建并**认领 Seller SKU**；公司算绩效时**也是按 SKU 落到小组**（每个小组卖了多少、产生多少利润、花了多少费用）。
- 让现有表与中台对接即可，**该表变更不多**，避免"这个系统维护一次、那个系统再维护一次 → 对不上"。

**本周新增**
- 做了一套 **DSP 分析链**的模板。⚠️ 会上提到"之前分析成 **W8K** 了，实际上是 **W8K2**"（**款号存疑，请核对**），**W8K2 刚做完一份，数据还没上传**。

**待验证：数据获取链路**
- A 发现 **Codex 上可以连到 AWS 上的分析平台**（结合后文"AMC 容器"，高度疑似 **Amazon Marketing Cloud**），但**会跳出一个外链**，出于安全考虑**不敢直接放进资料里试**。
- 会上共识：**这里的核心问题就是"数据怎么获取"** —— 走 API，还是走某种桥接？AWS 数据分析链路与 GPT 之间"肯定是有桥接的"。
- **唯一待验证项**：账户确认（确认账户后第三方应该能打通）。
- 【负责人】结论：**终极形态是 AI 直接从广告账户取数**，比"每周下一份报告"直接得多 —— 但**取决于亚马逊广告平台到底开放哪些接口**。

**AI 工具链 / 代理方案（A 汇报 + 负责人补充）**
- **方案一（自家）**：用阿里云**日本站服务器**做中转，代理接入 Codex 客户端，再分发给各处。
- **方案二（同行演示）**：用 **20x 账号**装在虚拟机上做**中转站**；一个账号对应一个中转站 + 独立隧道/代理；在 Codex 客户端里**选择中转站**再启动 Codex，即可正常使用 GPT 的 token。
  - **多账号轮换**：某账号触达上限进入"冷静期"时，**切到另一个中转账户接着用**；公司层面理论上**两三个账号循环就够**。
  - **可统计**：能看到每个用户消耗了多少 token。
  - 负责人点评："看起来也不是很复杂的样子。"
- **风险点（已识别）**：① 新开账户**目前买不到 20 倍套餐**（已下架）；② 存在一定的**代理风险**；③ 有人问"一个账号多 IP 分流会不会被 GPT 查封" → 解释是不会，因为实际用户都在**日本站的电脑**上，**出口 IP 很稳定**，甚至能**绕开翻墙影响**，国内可正常访问。
- **A 自己的用法**：不做消耗，走**账户级网页端数据** + **DeepSeek 的 agent 智能体**；写代码时也用**网页端免费流量**接入本地数据；**多 subagent 并发**写代码。机制是"把网页端当 API 用"，**中间有一条隧道连到本地**，把 DeepSeek agent 里的工作流和 **skills** 全部注入网页端。

### 4.2 管理侧定调（【负责人】）

> "大家要解决的问题是在于说，当整个团队都要用的时候，就变成一种情况 —— **人手一个 Codex**。"

- **三阶段判断**：
  1. **现在 = 探索阶段**：目标是**让大家先用起来**。不做各种约束，因为**每个人接受程度和使用效果不一样**，对 AI 熟悉程度也不够。
  2. **下一步 = 流程化**：真正从业务流程来讲，它是**需要流程化的** —— 做什么事、调用哪个 **skill**、怎么得到结果、结果传到哪。
  3. **终局 = 规模化 / SOP**：此时**账号和 token 必须够多**，不能"用着用着就触上限"。
- **规模化的代价（真实痛点）**：举例——"让他帮我写一个功能，**思考了三十多分钟，卡掉五小时上限**"。 → 流程化以后这类等待不可接受。
- **终极形态**：把能力**沉淀成一个个 agent**（"这个 agent 是做什么功能的"），大家按需调用即可 → 公司业务流程**相对 SOP 化**，**不再需要人人有账号**，也**解决了技能沉淀问题**，可复用、门槛低。
- **更远一步**：单一技能之后，可能直接在 AI 里把**全流程**跑完 —— 例如优化一个广告：从数据分析 → 调整建议 → 调整执行，**全在 AI 内完成**。

### 4.3 广告诊断 / DSP / 费用分摊（【B·广告与运营】）

**广告诊断**
- 已跟运营对齐了几个**广告媒体**和**产品广告组**的分析。
- **四个账号的口子做了自动更新**。
- 之前运营做测试的广告**共 79 个**：
  - **川鹏 ~70 多个**；
  - **洁博利 十几个**； ⚠️ 转写为"接过率"，经比对店铺名单判定为**洁博利**，请核对
  - 其他账号较少 —— 因为**很多测试此前已经做过**，在 B 这边属于复测。
  - 平均**每个运营测 5–10 个**。
- 现状：**分析报告基本已出**，但**效果与建议还在 VI 那边**，后面要给运营**对应策略**。

**DSP**
- 已摸清怎么投；对方（服务商）那边能看到的 **P+ 之类，我们这边基本都能看到，也能设置、能操作**。
- 已在账号里做了**功能测试 —— 除了没有点"启用"，其他操作都过了一遍**。
- 洁博利问能不能投 DSP → 结论见「决议 2」：**自投，不走服务商**。
- 判断依据补充：**衡量标准很重要** —— 原先账号可能做到 2 点多的指标就觉得自己优秀，看到别人做到更高，**才知道差距在哪**。所以外部方案**"就看一看"**，然后**自己也跑一个测试框**验证放大效果。
  - ⚠️ 关键前提：**如果 DSP 没有重复计算归因**，那就可以**放开投**（能投多少投多少）；但目前给的金额都比较小，**放大效果未知**。

**投放方法论（负责人）**
- 以前开广告活动**只有几个大类**（SP、关键词、自动、大词），往后可以**做得很细致**。
- 对比 AMS 那边的分享，坦言**"我们运营这边的广告做得还没那么精细化"**。
- 精细化后：**一条大链接可能有几十到三百个广告活动，每个各有作用** → 可以把**整体 ROI 往上提**。
- 所以运营的工作重点应该是**研究新形式**，而不是在原有广告上修补。

**广告费用分摊（本周进展）**
- 之前的分摊**不含 SP**，主要是搜索广告；**现在把 SP 算进去**，并做了**"含 SP vs 不含 SP"的花费对比**，数据**已上传云文档**（⚠️ 转写为"英文单"，**平台名待核**）。
- ⚠️ 价格波动较多，暂时未定论，"这个先发现其他"。
- **待办（已提）**：分摊目前只到**运营 / 小组级别**，**能否下沉到每个款式**？
  - 动机：运营自己核算单个款式时，"分到款式"更直观。**做一条链接时，肯定不是按子ASIN 算，而是按父ASIN 或单个链接/销售组算**。
  - 数据落脚点：多为 **SalesSKU 或 ASIN** —— **不改变分摊口径**，只是多加一层视图。
  - 利润算法：销售收入 − 各项费用 = 确切数字；**唯一没进系统的就是广告花费**（原先靠手动统计，会变、归因时间不同又会变）。
  - 痛点举例：**投的是 A 款，但 30% 成交出在 B 款**；**B 款自己没投广告，按新分摊法也要分摊** → 归因口径就解决这个。
  - 更实际的场景：**新款转化比不好，广告其实出在成熟链接上** → 只看账面会误判"新款广告亏得厉害"，**反映不出这个款到底好不好**。
  - **结论**：增加**"分到每个产品集合"**的表，**仍按月算**，但能落到款式。

### 4.4 视觉 / 图片生成 / 知识库（【C·视觉与知识库】）

**图片提示词实测**
- 用**通用图片提示词**做了测试：**童鞋**、**以前的两款鞋**、**冬季鞋**；结果**动态效果不错**，已发给对方看。
- 提示词原本在「第七个生成」环节用（⚠️ 表述含糊）；**亚马逊那边的 agent 也可以直接生成** —— 图方便的话可以直接用那边的。
- 主要瓶颈：**图片等待时间**。自建流程（**FLUX 那批**）也能批量生成很多个，但**对时间/吞吐有要求**。

**网页端**
- 为**加快推出**做了调整：**增加了管理员界面**，仍在调整中。
- 上线后先**把提示词放进去让运营使用**；后续**新增模块通过管理流程加入**。

**知识库方案（重点讨论）**
- 选型：**GitHub vs 付费仓库** → **GitHub 更合适**。
- **两级结构**：
  - **每个运营一个个人草稿库**；
  - **公司一个整体大库**；
  - 核验并符合规范后，**从个人库上传到公司库**；需要时（如 Codex 需要某技能）**从公司库拉下来用**。
- **Obsidian 的现状与局限**：
  - 自带同步（Sync）本质是**存到它自己的云端仓库**，感觉"也就那样"。
  - **它的双链是"假连接"** —— 各文档之间的链接**不是真连接**，`[[wikilink]]` 不等于可检索引用。
  - 因此：**知识库本身没有检索引擎能力**，主要充当**保存链路仓库**。
- **现状流程**：本地用 AI 做一轮 → 生成一个文件 → **钉钉上传一份 + 本地存一份**。
- **关键补充（C 提出，负责人认同）**：
  - **skills 很重要，必须有优先级排序**；
  - 需要一份 **`AGENTS.md`（智能体 MD 文件）** 来区分**哪些是团队首要技能、哪些是个人需要的**。
  - **单次任务的产出很杂乱**，要升级为"可共用的通用知识库 / skill"，**必须人工维护** —— "每一条分支链路都非常庞大"。
  - 流程：**每周做好 → 整理成可共用的 → 上传共享库 → 再拉下来**。
- **本地 agent vs web 端**：
  - 本地 agent **每次对话完都会保留一份 MD**；**web 端做不到**（除非走隧道）。
  - 负责人：**自己的仓库永远只有一个 `agent-master`**，不管用 Codex、WorkBuddy 还是 **DeepSeek Harness**，**都回归到这一个本地仓库**；仓库里接的是 **GitHub 上很火的那位（Karpathy）的三层架构**，`AGENTS.md` 里已定义架构，每次对话产出按架构回填。
  - ⚠️ 一个待解问题：**"你们俩的知识库没办法互相共享"** → Obsidian 有共享方案，但**还有没有别的方案，需要再研究**。
- **团队级视角（负责人）**：
  - 不管装本地还是装集中，**技能最终要能在团队里顺畅流转、能沉淀**。
  - 目标："同一个人或同小组做完分析，不需要别人去找他要" → **直接通过 AI 调用**，小组内甚至全公司都能查看/调用。
  - **长期议题：如何给整个公司建一个知识库** —— 沉淀一两年后量会很大，慢慢会形成**标准 SOP**。

### 4.5 负责人新增方向：品牌视觉统一（未来一个月主线）

- **问题**：现在每个品牌、每个页面**五花八门**，设置、字体各式各样。前期没有强约束、让大家自由做，**到最终是需要统一起来的**。
- **给 C 的任务**：**花时间研究，逐步做出规范**（色彩怎么选、字体、页面设置），以后生成时按规范走；**同一产品线的视觉最终形成相对统一的风格**，让用户更熟悉。**不要求马上落地**，但要**花几周有意识往这个方向学**。
- **背后逻辑**：这是**视觉影响 / 品牌营销**的概念 —— 理解概念后，再回来做这些事，**就能选出更有影响力的方式**。
- **C 的现状与思路**：
  - 当前提示词方向：图片生成**往"实拍、整体清新明亮"**靠。
  - 每个品牌看有无自身特征 —— **新华姐**提过 **WHITIN** 那边可能更多是**几何型**，**logo 要往那个方向靠**。
- **全局视野**：除了 **A+ 页面**，还有 **Brand Story**、投广告时的 **Logo**，都要统一到品牌表达上。
- **WHITIN 品线现状**：品线较多（**涉水/水鞋、四季、宽楦、动物鞋** 等，⚠️ 品线名转写存疑），但**各品线的视觉不统一**。
  - 目标：**根据品线特点 + AI 分析**，建议用**什么色调、什么 logo 字体**，最终各品牌之间**能统一/呼应起来**。
- **Logo 三条具体要求**：
  1. **风格不能变化太大** —— 要与**鞋子上的 logo 字体风格保持一致**；
  2. **比例上借助 AI 重新设计**；
  3. **适配多形态** —— 有的场景是长条、有的是正方形、甚至圆形 → **字体保持不变的前提下，通过颜色变化达到显示效果**。
- **主色调**：**不一定要统一到品牌级，统一到"系列"级即可** —— 针对不同产品线用不同主色调。
- **品牌故事**：要能在故事里**说服别人**。现状坦白："从我们自己品牌的发展来讲是**没有故事**的，就是为了卖货弄了一个商标。" 从营销角度讲，**必须有一个故事在那儿**（"要有一定的相对固定性"）。
- 以上作为**"接下去一个月，除主要工作之外的方向"**。
